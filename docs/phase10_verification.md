## 0. 이 단계가 하는 일

Phase 0부터 9까지 문서 13종, 코드 9개 모듈, 차트 12종을 만들었습니다. 그 과정에서 **값이 여러 번 바뀌었습니다.**

| 시점 | 변경 | 영향 |
|---|---|---|
| Phase 6 | 소프트웨어 인상률 3~10% → 6~15% | 손익분기점 60.2 → 44.2GB |
| Phase 9 | 시뮬레이션 500회 → 1,500회 | 중앙값 45.0 → 46.4GB |

값이 바뀔 때마다 관련 문서를 갱신했으나, **사람이 손으로 옮긴 숫자는 누락되기 쉽습니다.** 특히 위험한 것은 "본문은 고쳤는데 요약이나 권고표는 그대로인" 경우입니다. 한 문서 안에서 앞뒤가 어긋나면 읽는 사람이 어느 쪽을 믿어야 할지 알 수 없습니다.

**Phase 10은 그것을 기억이 아니라 실행으로 확인하는 단계입니다.** 코드를 돌려 정답을 구한 뒤, 문서에 그 숫자가 실제로 적혀 있는지 대조합니다.

## 1. 검증 방법

`src/verify_consistency.py`가 6개 범주 74개 항목을 자동 점검합니다.

| 범주 | 무엇을 확인하는가 | 항목 수 |
|---|---|---|
| 수치 | 코드 산출값이 문서에 그대로 적혀 있는가 | 15 |
| 일관성 | 한 문서 안에서 앞뒤가 맞는가, 옛 수치가 남아 있지 않은가 | 2 |
| 링크 | 문서 간 링크와 이미지 경로가 실제 파일을 가리키는가 | 22 |
| 원장 | 계산에 쓰이는 값이 모두 사용 가능 상태인가, 출처가 있는가 | 3 |
| 원칙 | 작업 원칙 13개 중 코드로 확인 가능한 것을 지켰는가 | 6 |
| 산출물 | 문서·차트·README가 모두 존재하고 정렬이 맞는가 | 26 |

**기존 테스트(126건)와 역할이 다릅니다.** 테스트는 *코드가 올바르게 동작하는가*를 봅니다. 이 검증은 *코드의 결과와 문서가 일치하는가*를 봅니다. 코드가 완벽해도 문서가 옛 숫자를 담고 있으면 산출물은 신뢰할 수 없습니다.

## 2. 발견한 문제

### 2.1 Phase 5 문서 전체가 갱신되지 않은 상태였습니다

**첫 실행에서 3건이 실패했고, 원인을 추적하니 하나의 누락에서 파생된 것이었습니다.**

Phase 6에서 소프트웨어 인상률을 상향 조정하면서 Phase 6과 Phase 8 문서는 갱신했으나, **선행 단계인 Phase 5 문서를 갱신하지 않았습니다.** 결과적으로 Phase 5에는 조정 이전 값이 그대로 남아 있었습니다.

| 위치 | 옛 값 | 실제 값 |
|---|---|---|
| 3.1 5년 손익분기 표 | 60.2 / 28.0 / 28.0 GB | **44.2 / 22.3 / 22.3 GB** |
| 3.2 3년 vs 5년 표 | 148.9 / 67.0 / 67.3 GB | **123.3 / 59.5 / 59.8 GB** |
| 3.2 기간 차이 배수 | 2.4~2.5배 | **2.7~2.8배** |
| 3.3 시나리오별 범위 | 61.4 / 60.2 / 55.2 | **45.8 / 44.2 / 38.9** |
| 5장 버린 것 표 | 2.4~2.5배 | 2.7~2.8배 |
| 11장 후속 우선순위 | 13.6~35.5GB | 11.1~27.0GB |

**왜 놓쳤는가.** 갱신 작업을 할 때 "인상률을 바꿨으니 인상률이 언급된 문서를 고치자"고 접근했습니다. 그런데 Phase 5에는 인상률이라는 단어가 없습니다. **인상률의 *결과*인 손익분기점만 적혀 있었습니다.** 원인이 아니라 결과가 실린 문서를 검색으로 찾지 못한 것입니다.

**같은 실수가 파생 수치에서 반복되었습니다.** Phase 5를 고친 뒤 다시 검색하니, 그 문서를 인용한 Phase 6의 한 문장("Phase 5에서 확인한 2.4~2.5배 차이")이 남아 있었습니다. 즉 **갱신은 한 번으로 끝나지 않고 연쇄를 따라가야 합니다.**

### 2.2 조치

전 수치를 현행 기준으로 갱신하고, Phase 5의 검증 이력에 **누락 사실과 사유를 기록**했습니다. 숨기지 않고 남긴 이유는, 이 사례가 "값이 바뀌면 결과가 실린 문서까지 추적해야 한다"는 교훈의 근거이기 때문입니다.

## 4. 예상 반론과 답변

분석을 검토하는 입장에서 제기될 만한 반론을 정리했습니다. **답변할 수 없는 것은 답변할 수 없다고 적었습니다.**

### 4.1 "가정값이 너무 많은 것 아닌가"

**타당한 지적입니다.** 공수 4건은 근거가 없고, Splunk·관리형 SIEM 단가는 해외 정가 앵커입니다.

다만 이에 대해 세 가지를 했습니다. 첫째, 근거 없는 값은 `assumed`로 **표시**하여 검증된 값과 구분했습니다. 둘째, 근거가 없을수록 **범위를 넓게** 잡았습니다(탐지룰 3~18인월, 6배). 셋째, 그 값들이 결론을 얼마나 흔드는지 **정량적으로 측정**해 손익분기점을 구간(37~56GB)으로 제시했습니다.

**가정을 없앨 수는 없었습니다.** 국내 SIEM 가격이 법령상 비공개이기 때문입니다. 대신 가정이 어디에 있고 얼마나 영향을 미치는지 드러냈습니다.

### 4.2 "특정 제품에 유리하게 계산한 것 아닌가"

**의도적으로 반대 방향의 조치를 여러 번 했습니다.**

| 조치 | 누구에게 불리한가 |
|---|---|
| 인상률을 시장 실측대로 상향(3~10% → 6~15%) | **상용 제품** |
| 자체 구축에도 오브젝트 티어링 옵션 부여 | **상용 제품** |
| SmartStore 원격 계층에 아카이브 정책 적용 | **SmartStore** |
| "계층화 없는 자체 구축은 전 구간 열세" 그대로 보고 | **자체 구축** |
| Dell판에서 "총액 효과 0.07%" 명시 | **Dell 접점 논거** |

특히 마지막 두 건이 중요합니다. **각 제안서에서 그 제안서의 논거를 약화시키는 사실을 스스로 밝혔습니다.**

### 4.3 "왜 이 6개 조합만 계산했는가"

선택지 5종의 조합은 10쌍이지만 6쌍만 계산했습니다. 동일 진영 내 비교는 "만들 것인가 살 것인가"가 아니라 "어떻게 구성할 것인가"의 문제이기 때문입니다.

**이 취사선택은 제안서 8장과 Phase 5 문서에 명시했습니다.** 계산하지 않은 조합이 있다는 사실 자체를 드러내는 것이, 유리한 조합만 골랐다는 의심을 방지하는 방법입니다.

### 4.4 "클라우드 기준인데 온프레미스에는 적용할 수 있는가"

**적용할 수 없습니다.** 이를 Dell판 5.2절에 명시했습니다.

온프레미스는 초기 도입비와 유지보수 계약이 발생하는 대신 월 사용료가 없어 비용 구조가 다릅니다. 다만 방향성은 말씀드릴 수 있습니다. 온프레미스에서는 "로컬 고성능 디스크 87% 감소"가 실제 하드웨어 구매액 절감으로 직결되므로 **효과가 더 클 것으로 예상**됩니다. 이는 추정이며 계산하지 않았습니다.

### 4.5 "국내 가격을 못 구했으면 분석의 근거가 약한 것 아닌가"

**국내 가격은 법령상 비공개입니다.** 「행정기관 및 공공기관 정보시스템 구축·운영 지침」 제17조에 따라 관련 정보가 공개 대상에서 제외되며, 이를 공공 제안요청서 5건 전수 확인으로 검증했습니다.

따라서 역산 방식을 택한 것은 편의가 아니라 **명문 근거에 따른 것**입니다. 다만 이로 인한 한계도 함께 밝혔습니다. 국내 보안관제 시장은 지정 업체만 진입 가능한 구조이므로, **실제 국내가가 해외 앵커보다 높을 가능성**이 있고 그렇다면 손익분기점은 분석값보다 뒤에 위치합니다.

### 4.6 "오류가 5건이나 나왔다는 것은 신뢰도가 낮다는 뜻 아닌가"

**반대로 해석하시기를 권합니다.** 오류 5건은 모두 *발견되어 수정된* 것입니다. 발견 경위를 보면 대부분 **결과가 이상해 보여 역추적한** 경우입니다.

| 오류 | 발견 계기 |
|---|---|
| 과금 단위(월↔일) | 관리형 SIEM 비용이 비현실적으로 낮게 나옴 |
| SmartStore 미차별화 | 두 선택지 결과가 완전히 동일하게 나옴 |
| SmartStore 원격 계산 | 결과가 예상과 반대 방향으로 나옴 |
| 차트 연차 누적 | 막대 높이와 라벨 숫자가 안 맞음 |
| 상수 중복 | 파일 점검 중 발견 |

**한 번도 의심받지 않은 계산은 검증된 계산이 아닙니다.** 각 오류는 재발 방지 테스트로 고정되어 있으며, 특히 차트는 부분 합이 총액과 일치하지 않으면 실행이 중단되도록 했습니다.

### 4.7 "몬테카를로가 통계 예측 아닌가"

**아닙니다.** 과거 데이터로 모델을 학습하거나 미래를 예측하지 않습니다. 이미 근거를 갖고 정해둔 low~high 범위 안에서 값을 무작위 추출할 뿐입니다.

이 구분은 프로젝트 방법론 선언(Phase 0)과 직결됩니다. 당초 로그 증가율에 시계열 예측을 도입하는 방안을 검토했으나, **방법론 충돌·실데이터 부재·우선순위 문제**로 폐기했습니다. 몬테카를로는 새로운 가정을 만들지 않으므로 그 선을 지킵니다.

### 4.8 "답변할 수 없는 것"

다음은 현재 분석으로 답할 수 없습니다.

- **특정 기업의 실제 로그량이 얼마인가** — 다단계 추정 시 오차가 곱해져 포기했고, 입력 변수로 전환했습니다
- **자체 구축 시 침해 확률이 얼마나 높아지는가** — 선택지별 확률 차이에 대한 통계가 존재하지 않습니다
- **탐지 규칙을 몇 개 만들어야 충분한가** — 성숙도 개념이지 완료 시점이 정의되지 않습니다
- **온프레미스 환경의 정확한 비용** — 계산하지 않았습니다

## 5. 남은 한계

| 항목 | 내용 | 왜 해결하지 않았는가 |
|---|---|---|
| RF·SF 기본값 | Splunk 클러스터 기본값 미확정 | 공식 문서에서 확인하지 못함. 사본 1벌을 기본값으로 두고 파라미터화 |
| Datadog 참고가 | 미착수 | 참고 비교군이며 결론에 영향 없음 |
| 자체구축 EPS 사이징 | 미확보 | 저장 용량 기준으로 대체하여 불필요해짐 |
| 항목 간 상관관계 | 몬테카를로가 독립 추출 | 상관계수 추정 근거 없음. 분산 과소 추정 가능성을 한계로 명시 |
| PowerScale 연동 | 미확인 | 접점 근거를 ECS로 한정 |

**이 표를 남기는 이유는 완결성을 주장하지 않기 위해서입니다.** 미해결 항목이 있다는 사실을 밝히는 것이, 모든 것을 해결했다고 주장하는 것보다 정확합니다.

## 6. 검증의 재현

```bash
python -m pytest tests/ -v            # 126건 — 코드 동작 검증
python src/verify_consistency.py      # 74건 — 문서·코드 일치 검증
```

두 검증 모두 난수 시드가 고정되어 있어 실행할 때마다 같은 결과가 나옵니다. `data/pricing.yaml`의 값을 변경하시면 두 번째 검증이 즉시 불일치를 보고하므로, **값을 바꾼 뒤 어느 문서를 갱신해야 하는지 자동으로 알 수 있습니다.**

## 9. 종합

프로젝트가 답하려던 질문에 대한 최종 답은 다음과 같습니다.

> **"오픈소스로 직접 만들면 되는데 왜 사야 하는가"**
>
> 5년 계약 기준으로 일일 로그량이 **약 46GB(80% 확률로 37~56GB 구간)** 를 넘으면 자체 구축이 유리해집니다. 단 **저장 계층을 분리했을 때에 한합니다.** 계층화하지 않은 자체 구축은 분석 전 구간에서 상용 제품에 열세였습니다.

## 0. 앞선 단계까지의 맥락

본 프로젝트는 기업이 보안 로그 분석 시스템(SIEM)을 직접 만드는 경우와 제품을 구매하는 경우의 총비용을 비교하여, 하루 로그량이 몇 GB를 넘어서면 구매가 유리해지는지를 계산하는 작업입니다. 기술영업 직군 지원을 위한 포트폴리오이며, 상세한 배경과 용어 설명은 `phase00_scope.md`에 정리되어 있습니다.

Phase 0에서 분석의 범위와 기준을 확정하였습니다. 대상은 Cisco Security 사업부이고, 비교 대상은 자체 구축과 관리형 SIEM과 Splunk이며, 계산 축은 일일 로그량 5~200GB이고, 대상 업종은 이커머스 중견기업입니다.

**본 단계에서 다루는 문제는 다음과 같습니다.** 비용을 계산하려면 대상 기업이 어떤 조건에 놓여 있는지를 먼저 알아야 합니다. 보안 담당 직원이 몇 명인지에 따라 인건비가 달라지고, 기록을 몇 년간 보관해야 하는지에 따라 저장 비용이 달라지기 때문입니다. Phase 1은 이 조건들을 확정하는 단계입니다.

## 2. 항목별 상세

### 2.1 보안 전담인력 비율 — 1.5 ~ 9.8%

전체 IT 인력 중 보안을 전담하는 인원이 차지하는 비율입니다.

**근거:** 무신사와 위메프의 정보보호 공시 자료에서 확인한 실측치입니다. 두 기업의 값을 각각 하한과 상한으로 사용합니다.

**이 값이 필요한 이유:** 자체 구축 방식의 비용은 대부분 인건비에서 발생합니다. 시스템을 직접 만들고 운영하려면 사람이 필요하며, 그 사람이 몇 명인지를 알아야 비용을 계산할 수 있습니다. 반면 제품을 구매하면 이 인원의 상당 부분이 절감됩니다.

**범위로 사용하는 이유:** 두 기업의 값이 여섯 배 이상 차이가 납니다. 이는 측정 오류가 아니라 기업마다 보안 조직 운영 방식이 실제로 크게 다르기 때문입니다. 따라서 평균을 내어 하나의 숫자로 만들 경우 어느 기업의 현실과도 맞지 않는 값이 됩니다. 프로젝트 공통 원칙 1항에 따라 범위로 유지합니다.

### 2.2 외주 비중 — 11 ~ 57%

보안 업무 중 외부 업체에 위탁하는 비율입니다.

**근거:** 위 2.1과 동일한 정보보호 공시 자료입니다.

**이 값이 필요한 이유:** 국내 기업은 보안 업무를 전부 내부 인력으로 수행하지 않습니다. 일부를 외부에 위탁하며, 이 경우 비용의 성격이 인건비에서 용역비로 바뀝니다. 자체 구축 방식의 인건비를 계산할 때 이 비중을 반영하지 않으면 비용이 과다하게 산정됩니다.

### 2.3 로그 보관 의무 기간 — 2년 (확정)

**근거 법령:** 개인정보의 안전성 확보조치 기준 제8조

**적용 조건:** 5만 명 이상의 정보주체에 관한 개인정보를 처리하는 경우

**이 항목의 중요성:** 본 프로젝트에서 가장 중요한 확정 사항입니다. 이유는 다음 세 가지입니다.

첫째, 이 조건은 선택 사항이 아니라 **법적 의무**입니다. 비용을 아끼기 위해 보관 기간을 줄이는 선택이 불가능합니다.

둘째, 저장 비용은 보관 기간에 정비례합니다. 2년 보관은 1년 보관의 두 배 용량을 의미하며, 이는 계산 결과에 직접적인 영향을 미칩니다.

셋째, **해외 자료와의 결정적 차이가 여기서 발생합니다.** 해외에서 작성된 SIEM 비용 분석 자료는 통상 90일에서 1년 보관을 전제로 합니다. 국내 기업에 그대로 적용할 수 없습니다. 이 항목이 본 프로젝트가 기존 자료를 옮기는 것이 아니라 국내 조건에 맞추어 새로 계산하는 작업이 되는 근거입니다.

### 2.4 일일 로그량 — 확정하지 않고 입력 변수로 처리 (판단 사항)

본 단계에서 내린 가장 중요한 판단입니다.

**당초 계획:** 대상 기업의 하루 로그 발생량을 추정하여 확정값으로 사용하는 방안을 검토하였습니다.

**추정 경로:** 월 방문자 수 → 페이지뷰 수 → 페이지뷰당 API 호출 수 → 호출당 로그 발생량 → 개인정보 접근 기록 건수 → 일일 총 로그량

**추정을 포기한 이유:** 위 경로의 중간 단계 중 상당수에 신뢰할 만한 업계 표준값이 존재하지 않습니다. 특히 페이지뷰당 API 호출 수와 개인정보 접근 건수는 서비스 구조에 따라 편차가 매우 큽니다.

추정을 여러 단계에 걸쳐 수행할 경우 각 단계의 오차가 더해지는 것이 아니라 **곱해집니다.** 각 단계에서 2배의 오차가 발생한다고 가정하면, 다섯 단계를 거친 최종값의 오차는 32배에 이릅니다. 이 값을 기준으로 계산한 결론은 근거로서의 가치를 갖지 못합니다.

**대신 채택한 방식:** 로그량을 확정하지 않고 사용자가 직접 입력하는 변수로 처리합니다. 최종 산출물은 "귀사의 로그량은 하루 30GB로 추정됩니다"가 아니라 "귀사의 로그량을 입력하시면 어느 방식이 유리한지 계산해 드립니다"의 형태가 됩니다.

**이 판단의 부수 효과:** 결과적으로 이 방식이 최종 산출물의 성격을 결정하였습니다. 프로젝트의 결과물이 하나의 보고서가 아니라 계산 도구가 된 것은 본 판단에서 비롯되었습니다. 추정이 불가능하다는 제약을 도구화라는 방향으로 전환한 사례로, 면접 시 설명 가치가 있는 판단입니다.

## 3. 검토 후 채택하지 않은 대안

| 검토한 대안 | 채택하지 않은 이유 |
|---|---|
| 로그량을 다단계 추정으로 확정 | 중간 단계의 표준값이 존재하지 않아 오차가 곱해집니다 (2.4 참조) |
| 보안인력 비율을 평균 단일값으로 사용 | 기업 간 실제 편차가 커 어느 기업의 현실과도 맞지 않게 됩니다 |
| 해외 자료의 보관 기간(90일~1년)을 준용 | 국내 법령상 2년 의무와 충돌합니다 |

## 5. 검증 필요 항목

본 문서의 수치는 이전 작업 과정에서 확보한 것으로, 저장소 공개 전 다음 사항을 보완할 예정입니다.

- 무신사 및 위메프 정보보호 공시 자료의 원문 링크와 공시 연도 명기
- 개인정보의 안전성 확보조치 기준 제8조 조문 원문 확인 및 개정 여부 점검

프로젝트 공통 원칙 2항에 따라, 출처 링크와 조회일이 확인된 항목만 최종 산출물의 근거표에 등재합니다.

## 0. 앞선 단계까지의 맥락

본 프로젝트는 기업이 보안 로그 분석 시스템(SIEM)을 직접 만드는 경우와 제품을 구매하는 경우의 총비용을 비교하는 작업입니다. 배경과 용어는 `phase00_scope.md`, 대상 기업 조건은 `phase01_organization_profile.md`, 비용 항목 목록은 `phase02_cost_structure.md`에 있습니다.

Phase 2에서 "무엇을 비용으로 볼 것인가"라는 목록을 확정했습니다. **Phase 3는 그 목록의 각 칸에 실제로 대입할 금액을 수집하는 단계입니다.** 목록만 있고 숫자가 없으면 계산이 불가능하므로, 이 단계가 계산 엔진(Phase 4)의 선행 조건입니다.

수집한 값은 모두 `data/pricing.yaml`(가격 원장)에 출처 URL·조회일과 함께 기록합니다. 코드에 숫자를 직접 적지 않는 이유는, 값이 바뀌었을 때 원장 파일만 교체하면 되도록 하기 위함입니다.

## 2. 확보한 값 — 항목별 근거

### 2.1 클라우드 단가 (서울 리전 고정)

개인정보 국내 보관 요건을 고려해 **서울 리전(ap-northeast-2)으로 고정**했습니다. 이 결정 자체가 Phase 7의 규제 항목과 연결됩니다.

**저장소 계층별 단가**

| 계층 | 서비스 | 단가 (USD/GB·월) |
|---|---|---|
| hot/warm (고성능) | EBS gp3 | 0.0912 |
| hot/warm (고IOPS) | EBS io2 | 0.1278 |
| cold (HDD) | EBS sc1 | 0.0174 |
| cold (처리량최적화) | EBS st1 | 0.051 |
| 오브젝트 (표준) | S3 Standard | 0.025 |
| 오브젝트 (저빈도) | S3 Standard-IA | 0.0138 |
| 아카이브 (즉시조회) | S3 Glacier Instant | 0.005 |
| 아카이브 (최저가) | S3 Glacier Deep Archive | 0.002 |

**계층 간 격차가 이 프로젝트의 핵심 숫자입니다.** 최상위(io2 $0.1278)와 최하위(Deep Archive $0.002)의 차이는 약 64배입니다. 전 구간을 고성능 SSD로 잡은 견적과 계층별로 나눈 견적의 차액이 곧 스토리지 티어링이 파는 가치이며, Dell 대응 지표가 됩니다.

**서울 리전 프리미엄 확인:** S3 Standard가 us-east-1 $0.023 대비 서울 $0.025로 **약 8.7% 높습니다.** 조사 초기에는 "타 리전은 5~30% 높다"는 막연한 서술만 확보되었으나, 공식 가격표 직접 조회로 실측을 확정했습니다.

**컴퓨트 단가 (서울 EC2 온디맨드, 월 환산)**

| 인스턴스 | 사양 | 월 요금 |
|---|---|---|
| m6i.xlarge | 4 vCPU / 16GB | $172.28 |
| m6i.2xlarge | 8 vCPU / 32GB | $344.56 |
| m6i.4xlarge | 16 vCPU / 64GB | $689.12 |

1년·3년 약정 시 30~50% 저렴해지므로 민감도 대상입니다. **실제 필요 대수는 사이징(2.3절)이 정해져야 산출 가능합니다.**

### 2.2 아카이브 인출 요금 — ISMS 리스크의 정량화

| 계층 | 저장 (GB·월) | 인출 (GB) | 배수 | 최소 보관 |
|---|---|---|---|---|
| Glacier Deep Archive | $0.002 | $0.022 (표준) | **11배** | 180일 |
| Glacier Instant | $0.005 | $0.03 | 6배 | 90일 |
| Standard-IA | $0.0138 | $0.01 | 0.7배 | 30일 |

**이 표가 Phase 7의 ISMS 리스크를 숫자로 만듭니다.** Deep Archive는 저장이 가장 싸지만 인출이 저장가의 11배이고 180일 최소보관이 걸립니다. 따라서 "아카이브 최저가 계층을 그대로 가정"하면, ISMS 심사 시 접속기록 조회 요구가 들어왔을 때의 비용이 누락됩니다. 아카이브 계층 설계 시 **연간 조회 빈도 가정을 반드시 명시**해야 합니다.

### 2.3 Splunk 인덱서 사이징 — 신뢰도 주의 항목

| 구성 | 인덱서당 처리량 |
|---|---|
| Splunk + ES(SIEM 기능) | **80~100 GB/day** |
| Splunk 단독 | 75~300 GB/day |
| HA 최소 노드 수 | **3대** |

**SIEM 기능을 켜면 처리량이 약 1/3로 떨어집니다.** 상관검색과 가속 데이터 모델이 단순 인덱싱보다 CPU와 디스크 IOPS를 훨씬 많이 소모하기 때문입니다.

**⚠ 신뢰도 한계 (반드시 명시):** 이 값들은 Splunk 공식 사양표가 아니라 **Splunk 공식 커뮤니티의 SplunkTrust 인증 전문가 및 Splunk 직원 답변**에서 나온 경험칙입니다. 네 개의 서로 다른 스레드에서 독립적으로 같은 값에 수렴하고, Cisco 레퍼런스 아키텍처(2TB/day에 인덱서 8대 = 250GB/day/대)와도 정합하나, 벤더가 보증하는 사양은 아닙니다. Splunk사의 공식 입장은 "정확한 산정은 세일즈 엔지니어·PS 아키텍트와 상담"이며, 이 태도 자체가 **값을 단일 수치가 아닌 범위로 처리해야 하는 근거**입니다.

**HA 3대 제약의 의미:** 부하 기준 필요 대수와 별개로 적용되는 하한입니다. 중점 구간(20~50GB/day)은 부하상 1대면 충분하나 클러스터 운영 시 3대가 최소이므로, **소규모 구간일수록 자체 구축의 컴퓨트 비용이 부하 대비 과도하게 계상됩니다.** 이는 손익분기점을 왼쪽으로 미는 요인이며, Phase 5에서 별도 분석 대상입니다.

### 2.4 Elastic 저장 오버헤드 — 계산 체계 분리

```
자체구축 총용량 = 일일량 × 보존일 × (1 + 복제본) × 1.15
```

1.15는 Lucene 인덱스 구조와 translog 오버헤드의 합입니다. **Splunk 계수(0.15/0.35)와 방향이 정반대**라는 점이 중요합니다. Splunk는 압축돼 원본보다 작아지지만(0.5배), Elastic은 오버헤드가 붙어 커집니다(1.15배). 두 체계를 혼용하면 계수를 잘못 빌려 쓰게 되므로 `src/storage_model.py`에서 함수를 분리했습니다(작업원칙 10항).

## 3. 관리형 SIEM 국내가 — 확보 불가 확정 및 역산 전환

본 절은 **"검토했다가 실패한 것과 그 이유"**의 기록입니다.

### 3.1 시도한 것

국내 관리형 SIEM(MSSP) 가격은 민간 벤더가 전부 비공개이므로, **공공 입찰 공고가 국내 실거래가에 가장 가까운 공개 자료**라고 판단해 나라장터를 조사했습니다.

- 검색: 나라장터 입찰공고, 공고명 "보안관제", 최근 365일
- 선별 기준: 낙찰방법이 `협상에의한계약`인 건(제안서 평가를 위해 과업내용을 공개해야 하므로 첨부가 충실). `수의시담`은 이미 업체가 정해져 첨부가 부실하므로 제외
- 확인: 제안요청서 5건 전수 조사 — 대검찰청, 한국은행, KLID(한국지역정보개발원), 보건복지부, 울산과학기술원

### 3.2 결과 — 5건 전부 데이터 볼륨 지표 없음

| 문서 | GB·TB | EPS | 로그량 |
|---|---|---|---|
| 대검찰청 (12.1억/년) | 없음 | 없음 | 없음 |
| 한국은행 (150.7억/4년) | 없음 | 없음 | 없음 |
| KLID (27.0억/년) | 없음 | 없음 | 없음 |
| 보건복지부 (51.2억/2년) | 없음 | 없음 | 없음 |
| 울산과기원 (1.01억/년) | 없음 | 없음 | 없음 |

### 3.3 원인 1 — 법령상 비공개 (교차 확인으로 밝혀낸 사실)

처음에는 "제안요청서에 원래 그런 정보가 없다"고 판단했으나, **교차 확인 결과 이 판단은 틀렸습니다.** 제안요청서에는 규모 정보를 담는 절이 실제로 존재합니다.

- 대검찰청: `2. 시스템 구성도` / `3. 관제시스템 운영 현황`
- KLID: `2. 정보화 현황`
- 보건복지부: `1. 청사 현황` / `2. 보안관제 업무 현황`
- 한국은행: `2. 세부 정보보호시스템 구성 현황`

그런데 해당 절의 내용이 삭제되어 있고, 대신 다음 문구가 들어 있습니다.

> "보안상 생략(제안서 작성에 필요한 경우, 별도 요청 시 열람 가능)"
> "「행정기관 및 공공기관 정보시스템 구축·운영 지침」 제17조(제안요청서 보안사항 등)에 따라 공개하지 않음"

같은 패턴이 5건 중 4건에서 확인되며, 한국은행은 열람 조건을 **5인 이내·1회 3시간·최대 3회**로 더 제한합니다. 열람하려면 기관 방문과 보안서약서 제출이 필요하고, 이는 입찰 참가 업체에게만 열린 절차입니다.

**따라서 국내 관리형 SIEM 규모·단가는 법령에 의해 구조적으로 비공개이며, 이는 프로젝트 작업원칙 3항(역산 처리)의 근거가 추측이 아니라 명문 규정임을 뜻합니다.**

### 3.4 원인 2 — 계약 단위가 GB가 아니라 인력

| 기관 | 계약 기준 | 연 환산 | 1인당 연 |
|---|---|---|---|
| 대검찰청 | **13명** (기획 1 / 침해대응·분석 4 / 보안관제 8) | 12.1억 | 약 9,300만원 |
| 한국은행 | 최소 **26명** | 37.7억 | 약 1억 4,500만원 |

**이 실측이 이번 조사의 최대 수확입니다.** 1인당 연 9,300만~1억 4,500만원이라는 범위는, Phase 1에서 SW산업협회 공시 통계로 확정한 인건비 범위(9,301만~1억 2,177만원)와 **거의 정확히 겹칩니다.** 즉 통계로 잡은 인건비가 실제 공공 계약 단가로 교차검증되었습니다.

부수적으로, **24시간 365일 관제에 8명이 필요**하다는 실무 기준도 확보했습니다(3교대 + 휴무 커버).

**단서:** 공공기관 계약이므로 민간 중견기업 단가와 차이가 있을 수 있어, 대리지표로만 사용합니다.

### 3.5 부수 확인 — 시장 진입장벽

조사한 5건 모두 **`보안관제전문업체(6526)` 업종 등록 업체만 입찰 가능**합니다. 국내 보안관제 시장이 지정 업체만 진입할 수 있는 구조라는 뜻이며, 이는 가격이 비공개인 구조적 이유이자 Phase 7(정량화 불가 요인) 등재 대상입니다.

### 3.6 전환 — 역산 방식

국내가 확보를 포기하고, 해외 공개가를 앵커로 삼아 역산합니다.

| 제품 | 공개 단가 | 성격 |
|---|---|---|
| MS Sentinel PAYG | $4.30(US East) ~ $5.59(US West) /GB | 주요 SIEM 중 유일하게 가격 공개 |
| MS Sentinel 100GB/day 약정 | $2.96/GB (31% 인하) | 중점 구간 근처 |
| MS Sentinel 90일 초과 보관 | $0.10/GB·월 | |
| Splunk | 약 $1,000/GB/년 (50GB 구간) | 제3자 추정 |
| Elastic | $0.55~1.10/GB | 제3자 추정 |

**역산 형태:** "국내 관리형 SIEM이 GB당 얼마 이하이면 자체 구축보다 유리한가"

## 7. 잔여 작업

| 항목 | 필요 조치 |
|---|---|
| 자체구축 노드 사이징 | EPS→GB/day 환산 가정을 세우거나, 축을 EPS 기준으로 바꿀지 결정 |
| Splunk 국내 인제스트가 | 역산 처리 (해외 정가 앵커 확보 완료) |
| Splunk 24개월 보관 곡선 | 선형 외삽 vs 계층 곡선 선택. 근거 명시 후 민감도 포함 |

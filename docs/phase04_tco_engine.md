## 0. 앞선 단계까지의 맥락

본 프로젝트는 기업이 보안 로그 분석 시스템(SIEM)을 직접 만드는 경우와 제품을 구매하는 경우의 총비용을 비교하는 작업입니다. 배경은 `phase00_scope.md`, 대상 조건은 `phase01`, 비용 항목 목록은 `phase02`, 수집한 단가는 `phase03`, 저장 용량 계산은 `phase03b`에 정리되어 있습니다.

**본 단계가 하는 일은 그 조각들을 곱해 실제 금액을 만드는 것입니다.**

지금까지 만든 두 조각은 각각 절반씩만 담당했습니다. `storage_model.py`는 "로그가 하루 100GB 쌓이면 디스크가 몇 TB 필요한가"만 계산하고 돈은 다루지 않았습니다. 가격 원장(`pricing.yaml`)은 "1GB 저장에 얼마인가"라는 단가만 갖고 있었습니다. Phase 4는 이 둘을 결합해 처음으로 금액을 산출합니다.

```
[입력] 일일 로그량 GB/day
   ↓ storage_model.py        (Phase 3.5 완료)   얼마나 필요한가
   ↓ pricing_loader.py       (본 단계 완료)      하나에 얼마인가
   ↓ cost_model.py           (본 단계 완료)      한 해에 얼마인가  ← 처음으로 금액 산출
   ↓ tco_engine.py           (본 단계 완료)      3년·5년 누적하면 얼마인가
[출력] 선택지별 총소유비용 + 손익분기 경향
```

## 1. 완료 사항

### 1.1 `src/pricing_loader.py` — 가격 원장 로더

원장을 읽어 계산 코드에 전달하는 계층입니다. 단순 파일 읽기가 아니라 **안전장치를 갖춘 접근 계층**으로 설계했습니다.

**핵심 기능 세 가지**

| 기능 | 내용 |
|---|---|
| 빈 값 차단 | `pending`·`blank`·`deprecated` 상태 항목을 꺼내면 예외 발생 |
| 환율 자동 환산 | 단위에 USD가 포함된 항목은 `get_krw()`가 환율을 곱해 원화로 반환 |
| 민감도 대상 추출 | `assumed`·`unverified` 항목을 자동으로 목록화 |

**빈 값 차단이 왜 중요한가.** 값이 비어 있는 항목을 조용히 0으로 처리하면 "자체 구축 서버비 0원" 같은 틀린 결과가 나오고, 그 결과가 그럴듯해 보여 발견되지 않습니다. 원칙 6항(코드 작업 전 실제 데이터 구조 확인)을 코드 수준에서 강제하는 장치입니다.

**민감도 대상 자동 추출.** Phase 6에서 이 목록을 그대로 분석 대상으로 사용합니다. 사람이 기억에 의존해 목록을 만들면 근거 약한 값을 빠뜨릴 수 있으므로, 원장의 상태 표기로부터 자동 생성되게 했습니다.

### 1.2 `src/cost_model.py` — 4개 비용 덩어리 계산

Phase 2에서 확정한 네 덩어리를 각각 별도 함수로 산출합니다.

| 덩어리 | 함수 | 발생 | 적용 |
|---|---|---|---|
| ① 소프트웨어 | `software_cost()` | 매년 | 자체구축 0원, 상용은 인제스트가 × (1+ES가산율) × 인상률 |
| ② 데이터 보관 | `storage_cost()` + `compute_cost()` | 매년 | 티어별 용량 × 티어별 단가 + 서버 대수 × 단가 |
| ③ 구축 인건비 | `build_cost()` | **1년차만** | 자체구축만. (초기구축+학습곡선+탐지룰) × 월급 |
| ④ 운영 인건비 | `ops_cost()` | 매년 | 일상운영 FTE × 연봉 + ISMS 공수 × 월급 |

**덩어리를 뭉치지 않은 이유.** 하나로 합쳐 총액만 내면 "인건비를 제외하면 언제부터 유리한가" 같은 질문에 답할 수 없고, Phase 6에서 항목별 영향도를 볼 수 없습니다. 분리 산출이 분석의 전제입니다.

### 1.3 `src/tco_engine.py` — 다년 누적 및 선택지 비교

`cost_model.py`가 산출하는 "한 해치 비용"을 계약 기간(3년·5년) 전체로 누적하고, 선택지들을 나란히 비교합니다.

**핵심 기능**

| 기능 | 내용 |
|---|---|
| 다년 누적 | 연차별 비용을 합산. 덩어리별 다년 합계(`bucket_total`)도 제공 |
| 로그량 증가 반영 | 방식 B(매년 증가) 기본, 방식 A(고정) 옵션 (2.4절) |
| 분석 상한 감지 | 로그가 증가해 200GB/day를 넘으면 경고 플래그 |
| 선택지 비교 | `compare()`가 전 선택지를 한 번에 계산, 정렬(`rank`)·최저값(`cheapest`) 제공 |
| 계산 불가 보존 | 원장 빈칸 등으로 계산 안 되는 선택지는 조용히 사라지지 않고 `errors`에 사유 기록 |

## 2. 확정한 것 — 설계 판단

### 2.1 관리형 SIEM 모델링 방식 — GB축 계산 + 인력 실측 병행

Phase 3에서 국내 관리형 SIEM 가격이 법령상 비공개임이 확인되었고, 확보된 국내 실측은 GB가 아니라 **인력 기준**(대검찰청 13명, 한국은행 26명)이었습니다. 이로 인해 계산 축을 어떻게 잡을지 결정이 필요했습니다.

| 검토안 | 내용 | 판단 |
|---|---|---|
| GB 단가로 통일 | 해외 앵커만 사용, 국내 실측은 문서에만 기록 | 실측을 버리게 됨 |
| 인력 N명 기준 | 로그량 → 필요 인력 수 환산 후 단가 적용 | **환산 근거가 없음.** 확보한 것은 인력 수뿐이고 그 기관들의 로그량은 지침 제17조로 비공개이므로 환산식을 만들 수 없음 |
| **병행 제시** | **엔진은 GB축으로 계산, 국내 실측은 별도 참고 지표로 표시** | **채택** |

채택 이유는 계산 축을 깨지 않으면서 실측도 살릴 수 있기 때문입니다. 인력 기준 모델링은 근거 없는 환산식을 새로 만들어야 해서 원칙 1항(추정을 쌓지 않는다)에 어긋납니다.

구현은 `managed_siem_kr_reference()` 함수로 분리했고, 함수 주석에 **"GB 단가 계산과 성격이 다르므로 직접 비교하지 않는다"**는 단서를 명시했습니다.

### 2.2 공수 5건 — 범위 가정 후 엔진 우선 완성

인건비 계산에 필요한 공수 값 5건에 표준 기준이 존재하지 않았습니다. 검색으로 근거를 찾는 방안과 범위 가정으로 두는 방안 중, **엔진을 먼저 완성하고 시간이 남으면 근거를 보강**하는 순서를 택했습니다. Phase 3의 관리형 SIEM 가격 조사에서 나라장터를 전수 확인하고도 값을 얻지 못한 경험에 비추어, 공수 역시 공개 자료가 존재할 가능성이 낮다고 판단했습니다.

| 항목 | low | base | high | 단위 | 근거 |
|---|---|---|---|---|---|
| 초기 구축 | 2 | 4 | 8 | 인월 | 없음 |
| 학습곡선 | 1 | 3 | 6 | 인월 | 간접(Elastic 숙련자 몸값 30~50% 프리미엄) |
| **탐지룰 개발** | **3** | **9** | **18** | 인월 | **전무** |
| 일상 운영 | 0.2 | 0.25 | 0.3 | FTE | 있음(엔지니어 시간의 20~30%가 클러스터 운영) |
| ISMS 대응 | 0.5 | 1.5 | 3 | 인월/년 | 없음 |

**범위 폭에 원칙을 반영했습니다.** 근거가 없을수록 넓게 잡았습니다. 탐지룰은 근거가 전혀 없어 6배(3~18), 일상 운영은 근거가 있어 1.5배(0.2~0.3)입니다. 좁게 잡으면 근거 없는 값이 정확한 것처럼 오인되기 때문입니다.

이를 표현하기 위해 원장에 **`assumed` 상태를 신설**했습니다. 계산에는 사용하되 민감도 분석 대상으로 자동 분류되는 상태입니다.

### 2.3 자체구축 노드 산정 — 저장 용량 기준 (EPS 환산 폐기)

자체구축 서버 대수를 구하려면 "노드 1대가 감당하는 양"이 필요한데, 처음 조사에서는 EPS(초당 이벤트) 기준 자료만 나왔습니다. 이를 GB/day로 바꾸려면 `GB → EPS → GB` 왕복 환산이 필요했습니다.

**이 방식을 폐기한 이유는 두 가지입니다.**

첫째, 환산 자체가 위험합니다. 조사 과정에서 **"환산 비율은 로그 소스 구성에 전적으로 의존하며, 가정된 환산은 벤더 비교를 30~50% 틀리게 만드는 일이 흔하다"**는 경고를 확인했습니다.

둘째, 프로젝트의 기본 판단과 충돌합니다. 본 프로젝트는 Phase 1에서 로그량을 추정하지 않고 **입력 변수로 두기로** 판단했습니다. GB를 EPS로 바꿨다가 되돌리는 것은 그 판단을 스스로 뒤집는 셈입니다.

**대안으로 저장 용량 기준 산정을 채택했습니다.** Elastic 공식 자료에서 근거를 확보했습니다.

| 기준 | 값 |
|---|---|
| 노드당 데이터 용량 (cold 보관 워크로드) | 최대 20TB (31GB heap 기준) |
| 디스크 사용률 상한 | 75~80% (워터마크 회피) |
| 채택값 | low 10TB / **base 15TB** / high 20TB |

Elastic 공식 문서가 **"샤드를 적절히 사이징하면 샤드 수 한계보다 디스크 공간이 먼저 바닥난다"**고 명시하여, 로그 보관 워크로드에서는 저장 용량이 노드 수를 결정하는 것이 실제에 부합합니다. 또한 `storage_model.py`가 이미 TB를 정확히 산출하고 있어 추가 환산 없이 바로 연결됩니다.

계산식은 `노드 수 = max(총 용량 ÷ 노드당 용량, HA 최소 3대)`입니다. HA 하한이 있어 소규모 구간에서는 부하와 무관하게 3대가 필요하며, 이것이 소규모 구간에서 자체 구축을 불리하게 만드는 요인입니다.

### 2.4 로그량 연차별 증가 — 방식 B 기본, 시계열 예측은 배제

5년 누적을 낼 때 로그량을 고정으로 볼지 매년 증가시킬지 결정이 필요했습니다.

| 방식 | 내용 | 판단 |
|---|---|---|
| A (고정) | 전 기간 동일 로그량 | 옵션으로 유지 |
| B (증가) | 매년 (1+증가율) 복리 적용 | **기본 채택** |
| (검토·폐기) 시계열 예측 | 과거 데이터로 ARIMA 등 학습해 미래 예측 | **폐기** |

**방식 B를 기본으로 한 이유:** 로그가 매년 는다는 것은 원장에 이미 확보된 전제이며, 이를 무시하면 자체 구축의 "나중에 용량이 터진다"는 특성이 드러나지 않습니다. 실제로 50GB/day 자체 구축 5년 누적이 고정 시 1,173백만원, 증가 반영 시 1,673백만원으로 **500백만원(43%) 차이**가 납니다.

**시계열 예측을 폐기한 이유(중요):** 통계 모델을 쓰면 통계 역량을 보여줄 수 있다는 검토가 있었으나, 세 가지 이유로 배제했습니다.

첫째, Phase 0의 방법론 선언("통계적 추론이 아닌 결정론적 모델링")과 정면 충돌합니다. 면접에서 "왜 통계 모델을 안 썼나"에 대한 답이 무너집니다.

둘째, 예측할 실제 데이터가 없습니다. "특정 이커머스 기업의 SIEM 로그량"의 과거 관측치는 공식 통계로 존재하지 않으므로, 시계열을 돌려도 결국 대리 지표 위에 또 다른 가정을 쌓는 것이 됩니다. 근거가 강해지는 게 아니라 겉모습만 정교해집니다.

셋째, 우선순위가 맞지 않습니다. 증가율보다 근거가 훨씬 약한 값(탐지룰 공수, 해외 정가 앵커)이 손익분기점에 더 크게 영향을 미칩니다. 통계 역량은 Phase 6 민감도 분석(몬테카를로 시뮬레이션 등)에서 활용하는 것이 방법론과도 부합하고 서사적으로도 강합니다.

**증가율 값의 근거:** 기존 20~30% 범위를 유지하되, IDC Global DataSphere로 출처를 격상했습니다. IDC는 전세계 데이터 생성·복제량 CAGR을 2020-2025 기준 23%, 2019-2024 기준 26%로 제시하며, 기업 데이터는 소비자 대비 2배 빠르게 성장한다고 명시합니다. 본 프로젝트의 20~30%가 이 범위와 정합함을 보이는 용도이며, **이 값은 "전세계 데이터 총량" 증가율이지 "특정 기업 로그량" 증가율이 아니라는 대리 지표 한계**를 원장에 명시했습니다.

## 3. 검토했다가 버린 것

| 버린 것 | 이유 |
|---|---|
| 관리형 SIEM을 인력 N명 기준으로 모델링 | 로그량 → 인력 수 환산 근거가 없음 (2.1절) |
| 공수 값을 검색으로 확보 | 표준 기준 부재 가능성이 높아 엔진 완성을 우선. 시간이 남으면 보강 (2.2절) |
| 노드 수를 EPS 환산으로 산정 | 왕복 환산이 결과를 30~50% 왜곡하며, GB/day 입력 변수 판단과 충돌 (2.3절) |
| 로그 증가를 시계열 예측으로 모델링 | 결정론적 모델 원칙과 충돌, 예측할 실제 데이터 없음 (2.4절) |
| 공수를 단일값으로 확정 | 근거 없는 값이 확정된 것처럼 보이게 됨. 범위 + 민감도로 처리 |
| 4덩어리를 하나로 합산 | 항목별 영향도 분석이 불가능해짐 |

## 4. 구현 중 발견해 수정한 오류

### 4.1 관리형 SIEM 과금 단위 오류

첫 계산에서 관리형 SIEM이 50GB/day 기준 연 400만원으로 산출되어 다른 선택지 대비 비현실적으로 저렴했습니다. 검증 결과 **단가 $4.30/GB를 월 단가로 착각해 12를 곱하고 있었습니다.**

이 단가는 "수집되는 GB마다" 부과되는 종량 요금이므로 하루 50GB를 수집하면 매일 50GB분이 과금됩니다. **365를 곱해야 합니다.**

| 구분 | 계산 | 결과 (50GB/day) |
|---|---|---|
| 오류 | $4.30 × 50GB × **12** × 환율 | 연 400만원 |
| 정정 | $4.30 × 50GB × **365** × 환율 | 연 1억 700만원 |

**약 30배 차이입니다.** 그대로 두었다면 관리형 SIEM이 전 구간에서 압도적으로 저렴하게 나와 결론이 완전히 뒤집혔을 오류입니다. `DAYS_PER_YEAR` 상수를 신설해 수정하고, 재발 방지를 위한 테스트를 추가했습니다.

**교훈:** 단가 항목의 `unit` 필드를 코드에서 확인하지 않고 관행적으로 월 단위를 가정한 것이 원인입니다. 원장에 단위가 명시되어 있었음에도 코드 작성 시 확인하지 않았습니다. 원칙 6항이 파일 구조뿐 아니라 **단위 확인**에도 적용되어야 함을 보여주는 사례입니다.

### 4.2 base 값 누락으로 인한 계산 중단

`splunk_es_uplift`(50~100%)와 `splunk_retention_over_90d`(30~50%)는 범위만 있고 base가 비어 있어 기본 계산이 중단되었습니다. 각각 중간값(75%, 40%)을 base로 채웠습니다.

다만 **의도적으로 base를 비워 둔 항목은 그대로 유지**했습니다. 보안인력 비율(1.5~7.1%)과 외주 비중(0~59%)은 기업 간 편차가 커 평균값이 어느 기업의 현실과도 맞지 않으므로, 범위로만 사용해야 하는 항목입니다.

## 5. 현재 산출 결과 (참고용, 확정 아님)

`tco_engine.py`로 로그량 증가(방식 B)를 반영한 5년 누적입니다. base 값 기준, 자체구축은 티어링 70% 적용.

| GB/day 시작 | 최저 | 2위 | ... | 최고 |
|---|---|---|---|---|
| 10 | 관리형 279 | Splunk 394 | | 자체구축 665 |
| 20 | 관리형 486 | Splunk 630 | | 자체구축 906 |
| 50 | **관리형 1,105 ≈ 자체+티어링 1,148** | | | 자체구축 1,673 |
| 100 | **자체+티어링 1,922** | 관리형 2,138 | | 자체구축 2,972 |

(단위: 백만원. 100GB 시작은 5년간 증가로 200GB 상한을 넘겨 경고 플래그가 섬)

**손익분기점의 첫 신호:** 50GB 부근에서 관리형과 자체+티어링이 만나고, **100GB에서 순서가 뒤집힙니다.** 프로젝트가 답하려던 "몇 GB부터 유리한가"의 첫 숫자입니다.

**증가 반영의 효과:** 50GB/day 자체구축이 고정(방식 A) 시 1,173백만원, 증가 반영(방식 B) 시 1,673백만원으로 500백만원 차이입니다. 로그 증가를 무시하면 자체 구축이 실제보다 유리하게 나옵니다.

**단, 이 숫자는 확정 결론이 아닙니다.** 공수 4건이 근거 없는 가정값이고, Splunk·관리형 단가가 해외 정가 앵커(실계약은 25~70% 할인)이며, 환율·증가율·인상률도 범위 가정입니다. Phase 6 민감도 분석 전까지는 경향 참고 수준으로만 다뤄야 합니다. 특히 100GB 이상 구간은 증가로 분석 상한을 넘겨 외삽이 되므로 신뢰도가 더 낮습니다.

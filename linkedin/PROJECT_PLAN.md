## 0. 이 문서의 위치

본 프로젝트는 기존 분석 프로젝트(SIEM 자체 구축 vs 구매 TCO)의 **후속 파생 프로젝트**입니다. 별도 저장소로 분리하지 않고 `linkedin/` 하위에 격리한 이유는 하나입니다.

**원 모델을 직접 import해서 호출해야 하기 때문입니다.** 필요 용량(`compute_capacity()`), 5년 비용(`compute_tco()`), 연도별 증가(`_volume_at_year()`)를 숫자로 옮겨 적지 않고 매번 호출해 받아야, 원장(`data/pricing.yaml`)이 곧 유일한 숫자 출처로 유지됩니다. 원 프로젝트의 근간이 *"코드에 숫자를 직접 적지 않으며, 값이 바뀌면 이 파일만 수정한다"*(pricing.yaml 서두)는 단일 원장 원칙이며, 저장소를 분리하면 값을 복사해야 해서 이 원칙이 깨집니다.

> **정정 이력:** 초판은 격리 이유를 *"가격 수집과 온프렘 모델 확장은 `data/pricing.yaml`과 `src/cost_model.py`를 직접 수정하는 작업"*이라고 적었습니다. 이후 §3.7(온프렘은 독립 비교표로만 사용)과 원 프로젝트 읽기 전용 원칙이 확정되어 **원 프로젝트를 수정하지 않게 되었으므로** 이유를 고쳤습니다. 결론(같은 저장소에 둔다)은 동일합니다.

| 구분 | 위치 | 성격 |
|---|---|---|
| 원 분석 프로젝트 | `docs/phase00~10`, `src/`, `data/`, `tests/`, `README*.md` | 완결됨. **읽기 전용** |
| 본 프로젝트 | `linkedin/L0~L6` | 진행 중. 원 모델을 **호출**해 그 결과를 콘텐츠화 |
| 원 프로젝트 검증 | `model_audit/` | **별개 프로젝트.** 원 프로젝트를 검증하고 승인받은 오류만 반영. 본 프로젝트 L2보다 먼저 |

원 프로젝트는 **어떤 파일도 수정하거나 새로 만들지 않습니다.** 수정이 필요하다고 판단되면 **원 프로젝트 검증(`model_audit/`)으로 보내** 그 승인 관문(보고 → 사용자 승인 → 수정)을 거칩니다(§3.13).

## 1. 배경 — 왜 이 프로젝트가 생겼는가

원 프로젝트는 "오픈소스로 직접 구축할 수 있는데 왜 구매해야 하는가"에 답하는 계산 도구를 만들었습니다. 결론은 손익분기 구간(약 46GB/day, 80% 구간 37~56GB)과 그 구간을 움직이는 요인들입니다.

그러나 그 산출물은 **읽는 사람이 이미 관심이 있어야 도달합니다.** 링크드인 카드뉴스는 그 반대 방향 — 관심이 없는 사람에게 먼저 도달해서, 자기 상황을 계산해 보게 만드는 경로입니다.

## 2. 목적과 전환 정의

**1차 목적:** 프리세일즈 / 세일즈 엔지니어 직군의 **영업 리드 생성**.

**리드의 조작적 정의 — 독자가 자기 로그량을 밝히는 순간.**

> "저희 하루 42GB 정도인데요"

이 한 줄이 리드입니다. 이유는 세 가지입니다.

1. 로그량을 밝히려면 먼저 **측정해야** 합니다. 측정했다는 것은 검토 단계에 진입했다는 뜻입니다.
2. 숫자 하나로 **퀄리피케이션이 끝납니다.** 구간을 알면 어떤 제품군을 논의할지 정해집니다.
3. 자기 숫자로 계산한 결과에는 **승복합니다.** 남이 추정해 준 숫자에는 승복하지 않습니다.

따라서 모든 카드는 마지막에 "당신의 숫자는 얼마입니까"로 수렴해야 하며, 독자가 **30초 안에 자기 숫자를 확인하는 방법**을 함께 제공해야 합니다.

**부수 목적:** 고객 언어로 번역하는 능력과 불리한 자료도 그대로 보고하는 태도의 공개 증명.

## 3. 대화에서 확정한 판단

기각한 것을 함께 적습니다. 원 프로젝트가 "검토 후 채택하지 않은 대안"을 기록한 것과 같은 이유입니다 — 기각 사유가 남지 않으면 같은 아이디어가 다시 올라옵니다.

### 3.1 기각 — 환율 변동 트리거

**당초 구상:** 환율이 상시 변동하므로 이를 트리거로 정기 콘텐츠를 발행한다.

**기각 사유:** 자체 민감도 분석이 이를 지지하지 않습니다. `docs/phase06_sensitivity.md` §4.1 기준, 환율 1,360 → 1,480원(+8.8%) 변동 시 손익분기는 44.8 → 41.7GB로 **3.1GB** 이동합니다. 5개 요인 중 5위입니다. 반면 몬테카를로 80% 구간은 37~56GB로 **폭이 19GB**입니다.

즉 환율 변동 효과가 **모델 자체 불확실성 폭의 약 1/6**입니다. "환율이 올라 구축이 유리해졌다"는 서술은 통계적으로 성립하지 않으며, 토네이도 차트가 README에 공개되어 있어 즉시 반박 가능합니다.

**대체:** 환율은 트리거가 아니라 **반증 소재**로 씁니다. "환율 8.8% 올라도 결론은 안 바뀝니다. 바뀌는 것은 갱신 인상률입니다." 반직관적이고, 자체 데이터가 그대로 뒷받침하며, 진짜 동인으로 독자를 유도합니다.

### 3.2 기각 — 기업 규모·재무정보에서 로그량 역산

**당초 구상:** 세금 지출 등 공개 재무정보로 특정 규모 기업의 로그 사용량을 간접 산출한다.

**기각 사유:** `docs/phase01_organization_profile.md` §2.4에서 이미 기각한 방법입니다. 다단계 추정은 오차가 더해지지 않고 **곱해지며**, 단계당 2배 오차만으로 5단계 후 32배가 됩니다. 재무정보 기점은 단계가 더 늘어납니다(재무 → 매출 → 트래픽 → PV → API 호출 → 로그량).

원 프로젝트는 이 기각을 근거로 "로그량을 입력 변수로 처리"했고, README는 그 판단을 *"결과물이 보고서가 아니라 도구가 된 이유"*로 제시합니다. 파생 프로젝트가 본편의 간판 방법론을 뒤집으면 양쪽 모두 무너집니다.

### 3.3 채택 — 구간(band) 방식으로 정밀도 요구를 낮춘다

로그량을 정확히 알 필요가 없도록 설계합니다. 몬테카를로 80% 구간이 37~56GB라는 것은 **모델 자체가 40GB와 50GB를 구분하지 못한다**는 뜻이므로, 독자의 숫자도 그만큼만 정확하면 충분합니다.

| 구간 | 서술 |
|---|---|
| ~37GB/day | 답 확정 |
| 37~56GB/day | **단정 불가 — 상담 구간** |
| 56GB/day~ | 답 확정 (티어링 전제) |

회색지대를 "모른다"고 명시하는 것이 오히려 신뢰를 만들고, 그 구간이 곧 상담 요청 구간이 됩니다.

### 3.4 채택 — 로그량 외 병용 축을 둔다

로그량 하나에 의존하지 않습니다. 자체 분석이 더 강한 축을 이미 갖고 있습니다.

| 축 | 답을 흔드는 폭 | 독자가 아는가 | 출처 |
|---|---|---|---|
| **계약기간 3년 vs 5년** | 44GB → **123GB (2.8배)** | **확실히 압니다** | README.ko §요약 |
| 소프트웨어 가격 인상률 | 29.7GB (1위) | 갱신 견적서에 있음 | phase06 §4.1 |
| **티어링 설계 여부** | 유리 ↔ **전 구간 열위** | 압니다 | phase05 |
| **인건비 흡수 가능 여부** | 44.2GB → **7.0GB** (vs Splunk는 교차 소멸) | **압니다** | §3.8 |
| 로그량 | 축 자체 | 측정하면 압니다 | — |

**계약기간이 로그량보다 답을 크게 움직이면서, 독자가 100% 아는 값입니다.** 로그량 추정 문제를 아예 우회하는 축이므로 시리즈 초반에 배치합니다.

### 3.5 채택 — 조달청 실계약가로 정가 앵커 문제를 해소한다

원 프로젝트의 최대 약점은 `docs/phase04_tco_engine.md` §에 스스로 적혀 있습니다 — *"Splunk·관리형 단가가 해외 정가 앵커(실계약은 25~70% 할인)"*.

조달청 나라장터 OpenAPI는 **실제 체결된 계약 단가**를 공개합니다. phase03에서 부딪힌 벽(「정보시스템 구축·운영 지침」 제17조에 따른 시스템 구성 비공개)은 *운영 시스템 구성*에 적용되며, *물품 계약 단가*는 공개 대상입니다. 온프렘 스토리지는 후자입니다.

이것이 성립하면 카드 문구가 "정가 기준"에서 **"조달청 실계약가 기준"**으로 바뀝니다. 방어 문구가 셀링 포인트가 됩니다.

### 3.6 보류 — 오픈소스 제품 분화

Elastic / OpenSearch / Wazuh / Graylog 분리는 이번 범위에서 제외합니다. 현재 `data/pricing.yaml`은 이들을 단일 오버헤드 계수(1.15) 하나로 묶어 처리합니다. 온프렘 확장과 동시에 열면 어느 쪽도 완결되지 않습니다. L6 이후 재검토합니다.

### 3.7 채택 — 온프렘 단가는 **독립 비교표로만** 쓴다

조달청 단가를 `data/pricing.yaml`·`src/cost_model.py`에 넣지 않습니다. "국내 조달 실계약가 대 AWS" 별도 비교표로만 사용합니다.

**근거:** 1회 구매(CapEx)와 월 과금(OpEx)을 하나의 숫자로 합치려면 감가 기간·유지보수율·전력·랙 가정이 필요하며, **그 가정이 결과를 좌우**합니다. 합치지 않으면 가정이 0개입니다. 과금 형태가 다르다는 사실을 그대로 제시하는 편이 근거가 강합니다.

또한 규격명에 RAID 표기가 전무해 raw/usable 판별이 불가한데(L1), 이를 추정으로 메우면 §3.2에서 기각한 다단계 추정에 다시 진입합니다. **"공시 용량 기준"이라고 명시**하면 추정 없이 성립합니다.

**결과:** 기존 L3(온프렘 CapEx↔OpEx 정규화)가 삭제되었습니다.

### 3.8 채택 — 인건비는 배제하지 않고 **시나리오로 병기**한다

**검토한 제안:** 운영 인건비를 양 진영 모두에서 제외한다. 근거는 ①오픈소스도 결국 사내 IT 인력이 투입되므로 양쪽 다 발생하고 ②인건비 정보를 확보하기 어렵다는 것.

**검증 결과 — 제외하지 않습니다.**

제외 시 손익분기 이동 (조합 1 = 오픈소스 직접 운영 + AWS, 티어링 70% 기준, GB/day) — **원 모델 산출값, 원 프로젝트 검증 대상(§3.13)**:

| | vs 관리형SIEM (5년) | vs Splunk (5년) | vs 관리형SIEM (3년) |
|---|---|---|---|
| 전체 비용 | **44.2** | **22.3** | **123.3** |
| 운영 인건비 제외 | 24.2 | 10.2 | 79.5 |
| 인건비 전부 제외 | **7.0** | **교차 소멸** | 11.4 |

> **정정 (2026-09-16):** 이 표는 원 모델 공식값 **44.2 / 22.3 / 123.3 · 24.2 / 10.2 / 79.5 · 7.0 / 교차 없음 / 11.4**(`docs/phase05`, `breakeven.find_breakeven`)를 **45 / 24 / 124 · 25 / 11 / 80 · 7 / 교차 소멸 / 12**로 옮겨 적었습니다. 원 프로젝트 검증 V1 재현 확인에서 발견해 바로잡았습니다. 또 원 프로젝트 검증 V5에서 오류만 고친 검증값 A는 **62 / 교차 없음(오픈소스 전 구간 저렴) / 157 · 39.2 / 교차 없음 / 115.5 · 17.3 / 교차 없음 / 33**입니다(승인 전, [`model_audit/AUDIT_REPORT.md`](../model_audit/AUDIT_REPORT.md) §3.4).

기각 사유 셋입니다.

1. **결론이 자동으로 한쪽으로 기웁니다.** 인건비 전부 제외 시 Splunk 대비 교차점이 사라져 전 구간 오픈소스 직접 운영 우위가 됩니다. 매 편이 "오픈소스 쓰세요"로 끝나며, 이는 §6-5(매 편이 "사세요"로 끝나면 안 됨)의 거울상입니다.
2. **원 프로젝트 간판 결론이 소멸합니다.** README 요약 첫 줄이 *"약 37GB 미만 → 구매. 인건비 부담이 라이선스 절감액을 초과합니다"* 입니다.
3. **근거가 가장 튼튼한 항목입니다.** 단가는 한국소프트웨어산업협회 「2025년 적용 SW기술자 평균임금」(통계승인 제375001호) 연 116,472,240원이며, 대검찰청(1인당 9,300만)·한국은행(1억 4,500만) 실계약으로 교차검증됩니다. `cost_model.py` 주석은 `ops_effort_daily`를 *"근거 확보된 유일한 공수 항목"*으로 명시합니다. 근거 부족을 이유로 뺀다면 `build_effort_*`(전부 `assumed`)가 먼저입니다.

**"양쪽 다 발생한다"는 지적은 이미 반영돼 있습니다.** `cost_model.py:293`은 ISMS 대응 공수를 양 진영에 동일 부과합니다. 50GB/day·5년 기준 인건비 비중은 오픈소스 직접 운영 32.5%, 관리형SIEM 6.1%, Splunk 5.1%로 **상용 쪽에도 계상**되어 있습니다. 모델은 공통 인건비와 오픈소스 직접 운영 전용 인건비를 이미 구분합니다.

**채택안 — 시나리오 병기.** "기존 IT 인력이 흡수하면 증분은 0"이라는 관점은 조직에 따라 참입니다(phase01: 보안 인력 비율 1.5~7.1%로 편차 큼). 따라서 배제가 아니라 **전체 / 운영 인건비 제외 / 인건비 전부 제외** 3종을 함께 제시합니다.

원 프로젝트가 이미 이를 설계해 두었습니다 — README: *"총액 하나로 합치지 않고 비용을 분류한 덕에, 이후 '인건비를 제외하면 어떠한가' 같은 질문에도 답할 수 있게 되었습니다."*

**부수 효과:** 로그량 외 병용 축이 하나 늘어납니다(§3.4). "귀사 보안팀에 여유 인력이 있습니까"는 독자가 즉시 답할 수 있는 질문이며, 답에 따라 결론이 44.2GB ↔ 7.0GB로 갈립니다(원 모델값).

### 3.9 채택 — 관리형은 버리지 않고 **1편 기준선**으로 쓴다

**검토한 제안:** 카드뉴스 목적이 "직접 구축 시 어떤 조합이 유리한가"이므로 위탁(관리형)을 범위에서 제외한다.

**기각 — 역할을 바꿉니다.**

1. **프로젝트 간판 수치가 전부 관리형 대비입니다.** 44.2GB/day, 80% 구간 37~56GB, 3년 123.3GB. 버리면 자산이 통째로 사라집니다.
2. **§6-5의 거울상이 됩니다.** 관리형을 빼면 직접 구축이 전제가 되어 매 편이 "직접 하세요"로 끝납니다.
3. **독자가 실제로 검토하는 선택지입니다.** 국내 시장에서 가장 흔한 형태입니다.

**채택안:** 관리형은 **"직접 구축이 얼마나 가치 있나"를 재는 기준선**입니다. 1편에서 위탁 vs 직접을 다루고 2편부터 직접 구축 4개 조합을 본론으로 다룹니다. 매 편에 관리형이 나올 필요는 없으며, 초점은 직접 구축에 두면서 기준선은 유지합니다. **스토리 흐름도 이 편이 자연스럽습니다.**

### 3.10 확인 — 소프트웨어와 인프라는 양자택일이 아니다

"오픈소스를 할지 인프라를 할지 가격을 비교한다"는 **틀린 프레임**입니다. 소프트웨어는 프로그램이고 프로그램은 인프라 위에서 돕니다. 직접 구축하면 두 축에서 **각각 하나씩 반드시** 고르며, 카드뉴스가 돕는 결정은 **4개 조합 중 무엇이냐**입니다.

### 3.11 채택 — "자체 구축"을 단독으로 쓰지 않고 풀어 쓴다

**발단.** "사내 장비로 사는 것도 결국 자기들이 사는 거니까 자체 구축 아닌가"라는 질문이 나왔습니다. 일상어와 국내 업계("구축형 대 구독형")에서는 맞는 말입니다. 그런데 원 프로젝트(phase00 §0.3)는 이 단어를 *오픈소스를 직접 설치·운영하는 방식*, 즉 **소프트웨어 기준**으로 정의했습니다.

**문제.** 같은 말이 반대로 읽힙니다. Splunk를 사내 장비에 설치하면 일상어로는 자체 구축, 원 프로젝트로는 구매입니다. 오픈소스를 AWS에 설치하면 그 반대입니다. 원 프로젝트의 "37GB 미만이면 자체 구축 불리"를 그대로 쓰면 독자는 *장비를 사면 불리*로 읽습니다. **질문자가 그렇게 읽었다는 것 자체가 독자도 그렇게 읽는다는 증거**입니다.

**채택안.**

| 뜻 | 쓸 표현 |
|---|---|
| 소프트웨어를 직접 설치·운영 (원 프로젝트의 뜻) | **오픈소스 직접 운영** |
| 장비를 직접 사서 보유 (일상·업계의 뜻) | **사내 장비 보유** · 사내 장비 |

적용 범위는 카드·비교표·링크드인 문서의 서술 전부입니다. 원 프로젝트의 제목·인용문, 코드 식별자와 옵션명은 원문을 유지합니다. L0·L1 결과 문서는 당시 기록이므로 고치지 않습니다.

### 3.12 채택 — 사내 장비 디스크 기준은 **서버 내장 드라이브**

**발단.** L2 수집 중 품명을 날짜 범위와 함께 다시 탐색하자 `하드디스크드라이브`(개별 드라이브)가 대량으로 잡혔습니다. 규격을 보면 스토리지 장비에 끼우는 순정 드라이브가 섞여 있어, L1에서 어레이 항목의 62%가 "용량 표기 없는 본체"였던 이유 — **본체와 드라이브를 따로 파는 구조** — 가 확인됐습니다.

**검토한 선택지:** (가) 드라이브로 교체 / (나) 드라이브와 어레이를 둘 다 표에 / (다) 계획대로 어레이 유지.

**(가) 채택.**

1. **카드뉴스는 직관적이고 간단해야 합니다.** "하드디스크 1TB에 얼마"는 설명이 필요 없습니다. 이것이 결정의 직접 사유입니다.
2. **원 모델의 AWS 계산과 조건이 같습니다.** 원 모델은 오픈소스 쪽을 *서버 + 서버마다 붙은 디스크 + 소프트웨어 복제본*으로 계산하며(`일일량 × 보존일 × (1 + 복제본) × 1.15`), 사내에서 이에 대응하는 것은 서버에 직접 꽂는 드라이브입니다.
3. **"디스크만" 비교가 성립합니다.** 어레이 값에는 케이스·제어 장치가 들어 있어 AWS 디스크 값과 조건이 어긋납니다.
4. **복제가 이중으로 들어가지 않습니다.** 어레이를 쓰면 소프트웨어 복제에 장비의 RAID가 겹칩니다.
5. **가격 정보가 훨씬 풍부합니다.** 같은 6개월에 나라장터 드라이브 911건·354개 모델·용량 표기 100%(어레이 362건·약 39%). 해외에도 TB당 가격 추적 사이트가 여럿 있으나, 미국 소비자가라 본표에는 쓰지 않습니다.

**기각** — (나)는 표가 복잡해져 목적에 맞지 않고, (다)는 2~4의 조건 불일치를 안고 갑니다. 어레이 수집분은 참고값으로 보존합니다.

**드러난 사실 — 상표가 크기보다 훨씬 큰 변수입니다.** 어레이용이던 "용량 구간 매칭" 규칙을 폐기하고 **상표 구분 + 등급 맞춤** 규칙으로 바꿨습니다.

#### 상표로 나누는 구조적 이유

1. **하드디스크 제조는 사실상 세 회사입니다.** Seagate·Western Digital·Toshiba가 출하량의 약 95%를 차지하며, IBM·Hitachi(HGST)·Fujitsu·Samsung·Maxtor·Quantum 등은 인수되거나 철수했습니다.
2. **서버·스토리지 회사는 이 세 회사에서 드라이브를 사서 자기 펌웨어와 상표를 입혀 팝니다.** 자사 장비와의 호환 검증을 거치고, 보증·지원을 장비와 묶어 제공합니다. 가격 차이는 이 검증·펌웨어·지원 값입니다.
3. **조달청 데이터가 이를 그대로 보여줍니다.** "제조사명"에 IBM·Hitachi Vantara·Fujitsu가 적힌 드라이브가 60개 이상인데, 이 회사들은 현재 하드디스크를 만들지 않습니다. 모델 번호도 IBM `AL3E`, Hitachi `DKC-F810I-…`, Fujitsu `ETRNCG-L`처럼 **자사 장비 부품번호**입니다.

#### 등급을 맞춰야 하는 이유 — 초안의 과장

개정 4판 초안은 제조사 상표 전체(141개)의 중앙값 105,233원을 썼습니다. 모델 번호로 등급을 판별하니 이렇게 섞여 있었습니다.

| 감시카메라용 (SkyHawk·WD Purple) | 49 | 84,900원 |

감시카메라용 기본형(SkyHawk)은 연간 작업량 한도가 **180TB**로, 데이터센터용 Exos(550TB)의 3분의 1입니다. 서버에 넣어 로그 검색을 돌릴 드라이브가 아니며, 비교 상대인 서버·스토리지 상표 드라이브는 전부 기업용 장비 부품입니다. 따라서 **제조사 상표 쪽은 데이터센터용만** 씁니다.

#### 2차 정정 — 가정 검증, 연결방식, 장비 용도

**① "기업용 장비 부품이면 데이터센터급" 가정은 일반론으로 틀립니다.** HPE는 드라이브를 Enterprise·Midline·Entry 세 등급으로 팔며, Entry는 부팅·백업용 저부하 제품(최대 4TB, 보증 1년)입니다. Dell도 PC·워크스테이션용을 기반으로 한 Entry 드라이브를 팔고, 이 드라이브는 RAID 구성이 안 됩니다.

그래서 112개 부품번호를 하나씩 확인했습니다.

| 판별 수준 | 개수 | 결과 |
|---|---|---|
| 확인 (판매처·제조사 문서에 명시) | 30 | 전부 니어라인 SAS 기업용 |
| 추정 (같은 장비 계열 문서) | 48 | 전부 니어라인 SAS 기업용 |
| 미확인 | 34 | Hitachi `R2H/S2K-…RSS` 12 · Dell 11 · 다민정보산업 5 · Pivot3 3 · Lenovo 2 · Infortrend 1 |

확인·추정분 78개 중 Entry 등급은 **없었습니다.** HPE Entry는 최대 4TB라 8TB 필터에서 걸러집니다. Dell Entry의 최대 용량은 확인하지 못했습니다.

**② 연결방식이 가격에 섞여 있었습니다.** 같은 제조사·같은 데이터센터 등급에서 SAS 36개 중앙 137,638원, SATA 32개 중앙 101,500원으로 **SAS가 약 1.36배**입니다. 서버·스토리지 상표는 확인·추정분이 전부 SAS이므로, 3.4배 안에 연결방식 차이가 들어 있었습니다.

단 1.36배는 용량 구성이 섞인 중앙값 비교입니다. **같은 용량끼리** 보면 8TB 1.16 · 10TB 1.39 · 12TB 1.56 · **14TB 2.90** · 16TB 1.11 · 18TB 1.03 · 20TB 1.19 · 24TB 1.26배로, 대부분 1.0~1.6배이고 14TB만 튑니다. 칸마다 1~11개라 얇습니다(§3.14 결정 과정에서 추가 확인).

**③ 비교 상대의 대부분이 디스크어레이 부품이었습니다.** 112개 중 **92개**가 IBM FlashSystem·Hitachi VSP·Fujitsu ETERNUS·NetApp E-Series·Infortrend 등 **디스크어레이·HCI 장비용**이었고(중앙 427,400원), **서버용은 14개**(Dell 13·Lenovo 1, 중앙 237,979원)뿐이었습니다. §3.12 본문이 비교 기준을 **서버 내장 드라이브**로 정했으므로, 비교 상대도 **서버용 부품**이어야 합니다.

| 맞춘 조건 | 제조사 상표 | 비교 상대 | 배율 |
|---|---|---|---|
| 없음 (초안) | 105,233 | 397,062 | 3.77배 |
| 등급 (1차 정정) | 115,800 | 397,062 | 3.43배 |
| 등급 + 연결방식 | 137,638 (SAS) | 404,448 (SAS 확인·추정) | 2.94배 |
| **등급 + 연결방식 + 용도** | **137,638 (SAS) / 101,500 (SATA)** | **237,979 (서버용)** | **1.73 / 2.34배** |

**결론 — 서버에 꽂는 드라이브끼리 보면 서버 회사 상표는 약 1.7~2.3배입니다.** 1차 정정의 3.4배는 디스크어레이 부품 가격이었습니다.

**당시 미결 — 제조사 상표 쪽 본값의 연결방식.** 서버용 14개 중 연결방식이 확인된 것은 2개(모두 SAS)뿐이라 짝을 정할 근거가 부족합니다. (A) SATA 101,500원 / (B) SAS 137,638원 / (C) 둘 다 표기 중 결정이 필요합니다. → **§3.14에서 (C) 둘 다 표기로 확정.**

**검증 과정의 교훈.** 검색 요약이 `ST14000NM0048`을 SATA라고 알려줬으나 판매처 여러 곳에서 **SAS**로 확인됐습니다. 모델 번호 규칙은 SATA판·SAS판 **쌍으로** 확인한 것만 씁니다.

### 3.13 채택 — 원 모델 산출값을 재검증한다 (링크드인과 별개 프로젝트로)

**발단.** 조합 1(오픈소스+AWS)·조합 3(Splunk+AWS)을 "원 프로젝트가 이미 계산했다"는 이유로 그대로 쓰면, 나중에 그 값을 쓸 때 부정확해서 산출값이 심각하게 왜곡될 수 있다는 지적이 나왔습니다. 전체 방향성은 유지합니다.

**타당합니다.** L2의 AWS 쪽 금액, L4 손익분기, L5 1편 기준선 비교, §4.1 비용 구성, §3.8 인건비 시나리오 표가 모두 원 모델 산출값입니다. 계획 수립을 위해 코드를 읽는 것만으로 의심 지점 15개가 보였고, 방향은 한쪽이 아니라 섞여 있었습니다.

**채택안 — 별개 프로젝트.** 검증 대상이 원 프로젝트이므로 링크드인 단계로 두지 않고 **원 프로젝트 검증 프로젝트(`model_audit/`)** 로 분리합니다. 링크드인과 별개로 진행하되 **순서는 L2보다 앞섭니다.** 정본 계획은 [`../model_audit/AUDIT_PLAN.md`](../model_audit/AUDIT_PLAN.md)입니다.

- 오류가 나오면 `model_audit/findings/`에 **원 프로젝트 phase별 파일**로 기록하고, 보고 후 **사용자가 승인한 항목만** 원 프로젝트에 반영합니다.
- 원 프로젝트 수정 후보는 어디서 발견했든 이 관문으로 보냅니다. 링크드인 쪽에 있던 S3 구간 체감 별건과, L3의 확인 항목 2개(Splunk Cloud 앵커 정합성·오픈소스 유료 지원)를 옮겼습니다.
- 검증이 끝나기 전까지 원 모델 산출값에 기댄 수치는 카드에 쓰지 않습니다. 원 프로젝트가 수정되면 본 문서의 해당 수치를 갱신합니다.

> **폐기 이력:** 같은 날 링크드인 단계 **L2-0 — 원 모델 AWS 경로 재검증**으로 먼저 신설했습니다(세부계획 작성, 문서 반영까지 진행). 원 프로젝트에 대한 검증은 링크드인 프로젝트와 별개로 진행해야 한다는 지시에 따라 **L2-0을 폐기**하고 위 구조로 옮겼습니다. 그 초안은 의심 지점을 "대부분 오픈소스에 불리한 한 방향"이라고 요약했으나, 오픈소스 쪽 비용을 줄이는 지점도 있어 이관 시 "방향이 섞여 있음"으로 고쳤습니다.

### 3.14 채택 — 제조사 상표 드라이브는 **SATA·SAS 두 값을 병기**한다

**발단.** §3.12 2차 정정에서 남은 미결 — 제조사 상표 데이터센터용 드라이브의 본값을 (A) SATA 101,500원 / (B) SAS 137,638원 / (C) 둘 다 중 무엇으로 할지. 질의응답에서 두 방식의 존재 목적과 근거를 따져 본 뒤 결정했습니다.

**두 방식의 존재 목적.** 둘 다 2000년대 초 병렬 케이블을 직렬로 바꾼 후속 규격입니다.

| | SATA | SAS |
|---|---|---|
| 조상 | ATA(IDE) — PC의 디스크 연결 | SCSI — 서버의 디스크 연결 |
| 목적 | 컴퓨터 한 대에 디스크를 싸게 붙이기 | 서버·저장 장비에 디스크를 많이, 여러 서버에 붙이기 |
| 한 선에 붙는 디스크 | 1개 | 확장 장치를 거쳐 매우 많이 |
| 선 길이 | 약 1m | 약 10m |
| 디스크당 통로 | 1개 | 2개 (서버 두 대가 같은 디스크에 접근) |
| 속도 | 6Gb/s | 12Gb/s |
| 호환 | — | SAS 슬롯에 SATA 디스크 장착 가능 (반대는 불가) |

하드디스크 한 개의 속도(약 2.3Gb/s)는 SATA 대역폭도 다 쓰지 못하므로, 하드디스크에서 두 방식을 가르는 실질적 차이는 **디스크당 통로 2개**(한쪽 서버·컨트롤러가 멈추면 다른 쪽이 이어받음)입니다. SAS가 비싼 이유로는 회로가 조금 더 복잡하고, 판매량이 적고, 기업용 기능(양방향 동시 통신, 전송 중 손상 검사 등)이 들어 있고, 대체재가 없는 구매자(디스크어레이)가 산다는 점이 일반적으로 거론됩니다. 제조사가 원가 구성을 공개하지 않으므로 요인별 비중은 알 수 없습니다.

**근거 대조**

| 근거 | 가리키는 쪽 | 한계 |
|---|---|---|
| 서버 내장은 "컴퓨터 한 대에 디스크"로, SATA의 존재 목적과 일치. 디스크어레이는 SAS의 목적과 일치 | SATA | 구조 논리일 뿐 실제 구매 관행 확인이 아님 |
| 하드디스크는 SATA 대역폭도 다 못 씀 | SATA | SAS를 고르는 이유는 속도가 아니라 이중 통로라 반박력이 약함 |
| 오픈소스는 소프트웨어가 복제본을 만들므로(원 모델 "복제본 1벌") 디스크 쪽 이중 통로 가치가 낮음 | SATA | 추론 |
| 서버 회사 상표 서버용 14개 중 연결방식을 확인한 2개가 모두 SAS | SAS | 표본 2개 |
| SNIA 2023년 1월 발표가 TrendFocus 자료로 하드디스크 SATA 대 SAS 약 75 대 25를 제시했다는 검색 요약 | SATA | **원문 미열람**(웹 요청 403, 브라우저는 봇 확인 화면에서 중단) · 전체인지 대용량 서버용인지 불명 |
| Backblaze 공개 디스크 통계 — 모델 번호로 판별되는 제품(`HUH721212ALE604`, `MG07ACA14TA`, `ST16000NM001G` 등) 전부 SATA. 저장 장비도 SATA 컨트롤러로 설계 | SATA | 한 회사. 초대형 클라우드 회사(AWS·구글·MS·메타)는 미확인 |
| 메타 공개 저장 장비 설계(Bryce Canyon)는 SAS·SATA 둘 다 지원 | 판단 불가 | 실제 구매 디스크는 비공개 |

**(C) 채택. 둘 중 하나를 고를 근거가 부족하면, 카드 한 장을 늘리더라도 둘 다 싣습니다.** 사내 드라이브 본값은 **제조사·SATA / 제조사·SAS / 서버 회사 상표** 3개입니다.

**기각** — (A)만 실으면 SAS를 쓰는 독자에게 AWS 대비 배율이 과장됩니다(50GB/day 예시 약 24배 대 18배). (B)만 실으면 확인 표본 2개에 기대게 되고 SATA를 쓰는 독자에게는 반대로 작아집니다.

**비용** — 비교표에 칸 하나, 카드에 연결방식 설명 한 장(L5)이 늘어납니다. §3.12 사유 1(카드뉴스는 간단해야 함)과 부딪히지만, 근거 없이 하나를 고르는 것보다 낫다고 판단했습니다.

> **정정 기록:** 결정 직전 질의응답에서 확인 없이 말한 것이 두 가지 있었습니다. 문서에는 적지 않았으나 결정 근거와 맞닿아 있어 남깁니다. ①"대형 클라우드 회사도 값 때문에 주로 SATA를 쓴다" — 위 표대로 확인된 것은 Backblaze뿐입니다. ②"클라우드 서버는 컨트롤러가 보통 하나라 두 번째 통로를 꽂을 곳이 없다" — Bryce Canyon에 디스크만 든 상자를 다른 서버에 연결하는 구성이 있어 일반론으로 틀립니다. 다만 그 구성에도 SATA 디스크를 꽂을 수 있어 SAS를 강제하지는 않습니다. 또한 "SAS가 SATA보다 비싸다"는 방향을 한때 거꾸로 이해한 질문이 있었고, 조달청 표본으로는 SAS가 비쌉니다.

## 4. 전체 구조 — 결정 트리

**SIEM 도입 비용 = 소프트웨어 + 인프라 + 인건비의 합입니다.** 소프트웨어와 인프라는 경쟁 관계가 아니라 더하는 관계이며, 라이선스 가격이 곧 TCO가 아닙니다. SIEM은 프로그램이며, 돌아갈 서버·로그를 담을 디스크(2년 보관 의무)·운영할 사람이 추가로 필요합니다.

### 4.1 실측 비용 구성 (50GB/day · 5년 · 티어링 70%, 백만원)

> **원 모델 산출값입니다. 원 프로젝트 검증 전이므로 카드에 쓰지 않습니다(§3.13).**

| | 소프트웨어 | 인프라 | 인건비 | 합계 |
|---|---|---|---|---|
| 조합 1 — 오픈소스 직접 운영 + AWS (티어링) | **0** | **774 (67.5%)** | 373 | 1,148 |
| 관리형 SIEM | **1,122** | **0** (벤더 부담) | 73 | 1,195 |
| Splunk | **1,251 (87%)** | 114 | 73 | 1,438 |

**비중이 뒤집힙니다.** 오픈소스 직접 운영은 인프라 싸움, 상용은 라이선스 싸움입니다. 인프라 774를 다시 쪼개면 **순수 디스크 65% / 서버(EC2) 35%** 로, 디스크 단독이 총비용의 약 44%입니다.

### 4.2 결정 트리 — 2차원 매트릭스가 아닙니다

```
                    SIEM이 필요하다
                          │
            ┌─────────────┴──────────────┐
         위탁한다                      직접 한다
            │                            │
      관리형 SIEM               ┌─────────┴─────────┐
   소프트웨어·인프라·운영     소프트웨어축        인프라축
      전부 벤더               오픈소스 / Splunk   AWS / 사내장비
            │                       └────┬────┘
      서비스료 1건                  2 × 2 = 4개 조합
```

**관리형은 소프트웨어축의 선택지가 아닙니다.** "설치할 것인가 말 것인가"라는 앞단 결정이며, 위탁을 고르면 그 아래 두 축이 사라집니다.

> **정정 이력:** 최초 작성 시 관리형을 소프트웨어축의 세 번째 선택지로 분류했으나 틀렸습니다. 관리형은 소프트웨어·인프라·운영을 모두 벤더가 대므로 두 축 어디에도 속하지 않습니다.

**직접 하기로 했으면 두 축에서 각각 하나씩 반드시 고릅니다.** 오픈소스를 골라도 인프라는 여전히 필요합니다(§3.10).

| 경로 | 소프트웨어 | 인프라 | 원 프로젝트 | 담당 |
|---|---|---|---|---|
| 관리형 위탁 | — | — | 계산됨 (국내가 문제) | L3 |
| 조합 1 | 오픈소스 | AWS | 계산됨 = "자체구축" | — |
| 조합 2 | 오픈소스 | 사내장비 | **미계산** | **L2** |
| 조합 3 | Splunk | AWS | 계산됨 | L3 (가격 품질) |
| 조합 4 | Splunk | 사내장비 | **미계산** | **L2** |

**"자체구축"은 소프트웨어 축의 개념이며 하드웨어 구매와 무관합니다.** phase00 §0.3 정의는 *무료로 공개된 소프트웨어(오픈소스)를 직접 설치·운영하는 방식*입니다. AWS는 빈 서버와 빈 디스크만 제공하고 SIEM을 제공하지 않으므로 AWS 위에서도 자체구축이 성립합니다.

phase00 §2.2의 비교 대상은 자체구축 / 관리형 / Splunk 3종이며 **인프라는 축에 포함되지 않습니다.** phase03에서 공개 가격을 확보할 수 있는 것이 AWS뿐이어서 인프라가 AWS로 고정되었습니다. **맹점이 아니라 의도적 범위 설정입니다.**

### 4.3 관리형 비용 해석 주의

`software_cost()`가 관리형 서비스료를 **통째로 `software` 버킷에 넣습니다.** §4.1 표의 관리형 1,122는 소프트웨어 값이 아니라 **벤더의 인프라·인건비가 녹아 있는 올인 서비스료**입니다. 인프라 0·구축 0은 비용이 없어서가 아니라 그 안에 포함되어 있어서입니다.

또한 모델 단가는 MS Sentinel 해외 앵커($4.30/GB)인데, **국내 계약은 인력 기준**이며 24시간 관제에 **최소 8명**이 필요합니다. 8명 × 1인당 9,300만~1억 4,500만원이면 5년 37억~58억으로, 모델 값 11.95억의 **3.1~4.9배**입니다. 단 공공기관 대형 사례이므로 대리지표로만 씁니다.

### 4.4 현재 확보된 것과 부족한 것

### L1 — 나라장터 API 스파이크 ✅ 통과(조건부)
**질문 하나에만 답합니다:** 조달청 OpenAPI에 온프렘 스토리지 단가가 **쓸 만한 형태로** 존재하는가.

확인 항목 — ① 품목 분류에 스토리지 장비가 잡히는가 ② 용량(TB) 필드가 구조화되어 있는가 ③ 벤더 식별이 가능한가 ④ 단가가 총액인가 단위당인가.

**중단 조건:** ①~③ 중 둘 이상이 불가하면 트랙 B를 폐기하고 해외 리스트가(트랙 C)로 후퇴합니다. 이 판단은 **모델을 짜기 전에** 내려야 합니다.

대상 API — [종합쇼핑몰 품목정보](https://www.data.go.kr/data/15129471/openapi.do) · [나라장터 계약정보](https://www.data.go.kr/data/15129427/openapi.do) · [나라장터 낙찰정보](https://www.data.go.kr/data/15129397/openapi.do)

**선행 조건:** 공공데이터포털 활용신청 후 인증키 확보.

### L2 — 디스크 단가 비교표 (인프라축 중 디스크) ⬅ 다음 · 원 프로젝트 검증 이후 재개

> AWS 쪽 금액(460.7~559.9백만원)과 배율(약 10~24배)은 원 모델 산출값에 기대므로 **원 프로젝트 검증(§3.13) 결과로 바뀔 수 있습니다.** 드라이브 수집·분류는 검증과 무관합니다.

**구하는 것:** 로그를 담을 디스크를 **AWS에서 빌릴 때**와 **서버에 꽂을 하드디스크를 사서 쓸 때**의 가격 비교표. **오픈소스 직접 운영의 총비용이 아니며**, 소프트웨어·서버·인건비는 다루지 않습니다. 조합 2·4 공통입니다. 사내 장비 쪽 기준은 **서버 내장 드라이브**입니다(§3.12).

**조합별 무게가 다릅니다** (50GB/day · 5년). 디스크가 총비용에서 차지하는 비중이 조합 2 쪽(오픈소스) **43.5%**, 조합 4 쪽(Splunk) **1.4%** 입니다.

**산정 규칙**

1. 용량은 **5년차 최대치** — 50GB/day 조합 2는 84.0 → 174.1 / **205.0** / 239.8TB (증가율 20/25/30%). 복제본 1벌은 모델 공식에 포함, RAID 미고려
2. AWS 5년은 **연도별 증가 반영 누적** — 같은 조건 460.7 / **508.1** / 559.9백만원
3. 드라이브 단가는 **상표·용도·등급·연결방식을 맞춤** — 제조사 3사는 **데이터센터용만**, 서버 회사 상표는 **서버용 부품만**(디스크어레이 부품 제외), SATA·SAS 구분 기록. 제조사 쪽은 **SATA·SAS 두 값 병기**(§3.14) — 사내 드라이브 본값 3개
4. 드라이브 크기는 **8TB 이상**
5. 증가율은 원장 **low/base/high 3값을 모두** 사용
6. 드라이브 개수는 **정수로 올리지 않음**

**수집 경로**

- **나라장터** — 종합쇼핑몰 품목정보, 품명 `하드디스크드라이브`. API가 현재 유효한 카탈로그만 돌려주므로 실제 데이터는 등록일 2025-10 이후
- **AWS** — Price List **Bulk API**(인증 불필요). S3 서울 JSON 전체, EC2/EBS 서울 CSV 202MB는 줄 단위로 읽으며 필터링

**참고 표본 기준 예시** (50GB/day 조합 2, 205TB, AWS 5년 508.1백만) — 사내 드라이브 1회 **20.8백만(제조사·SATA) / 28.2백만(제조사·SAS) / 48.8백만(서버 회사 상표 서버용)** → **약 24배 / 18배 / 10배**. L2에서 확정합니다.

> **정정 이력:** ①초판 L2는 AWS Query API 사용, `src/pricing_fetch/` 신설, `pricing.yaml` 필드 추가, 원장 출처 등급 상향을 계획했으나 앞의 것은 Bulk API로 확인되어, 나머지는 원 프로젝트 수정이라 폐기했습니다. ②"84TB, 310백만 대 11.5~33.6백만, 10~27배"는 로그 증가를 빠뜨리고 온프렘을 1년차 용량으로 잡은 오류였습니다. ③개정 2~3판의 "약 4~18배, 중앙 약 9배"와 "용량 구간 매칭" 규칙은 **디스크어레이 기준**이었으며 §3.12 전환으로 대체되었습니다. ④수집 기간을 2025~2026으로 넓혀 표본을 늘리려 했으나, API가 현재 유효 카탈로그만 반환해 2025년 1~9월은 비어 있었습니다.

세부계획: [`L2_pricing_fetch/L2_plan.md`](L2_pricing_fetch/L2_plan.md) (개정 4판 3차 보정)

### L3 — 국내 가격 미확보 항목 해소

> **기존 L3(온프렘 CapEx↔OpEx 정규화)는 §3.7 결정에 따라 삭제되었고, 그 자리에 신설되었습니다.** 삭제된 단계는 CapEx 연환산·유지보수·전력·랙·raw→usable 변환으로 구성되었으며, 전부 온프렘을 원 모델에 선택지로 넣기 위한 계층이었습니다. 넣지 않기로 했으므로 필요가 사라졌습니다.

> **개명 이력:** 최초 "SIEM 소프트웨어 가격 수집 (소프트웨어축)"으로 명명했으나, 대상에 관리형이 포함되고 관리형은 소프트웨어축이 아니므로(§4.2) 정정했습니다.

대상은 **국내가를 못 구해서 품질이 낮은 항목 2개**이며 원인이 같습니다.

| 항목 | 현재 근거 | 문제 |
|---|---|---|
| Splunk | 해외 정가 앵커 | **실계약 25~70% 할인** |
| 관리형 SIEM | **역산(derived)** | 국내가 비공개 · 인력 기준 계약 |

이것이 원 프로젝트 최대 약점입니다. `docs/phase03_pricing_data.md`가 「행정기관 및 공공기관 정보시스템 구축·운영 지침」 제17조 비공개 벽에 막혀 역산을 채택했습니다.

**단서.** L1 탐색 중 나라장터 종합쇼핑몰에 대분류 `소프트웨어`가 가격과 함께 등록돼 있음을 확인했습니다(예: 통신서버소프트웨어 10,300,000원, 제조사·규격명 필드 동일). 스토리지와 같은 API·같은 필드 구조입니다.

**위험 2가지 — 반드시 스파이크로 먼저 판정합니다.**

1. 사무용 S/W는 등록돼 있어도 **SIEM 같은 특수 보안 제품은 조달 등록이 없을 수 있습니다.**
2. phase03이 발견한 대로 **국내 보안 계약은 물품이 아니라 인력 기준 용역**입니다(대검찰청 13명 12.1억, 한국은행 26명 37.7억). 용역이면 물품 카탈로그에 존재하지 않습니다.

**판정 질문:** "보안 소프트웨어가 조달 카탈로그에 **물품으로** 잡히는가."
**중단 조건:** 잡히지 않으면 즉시 접고, Splunk 정가 앵커와 관리형 역산을 그대로 유지합니다.

L1에서 인증 문제로 소모한 전철을 밟지 않도록 판정을 최우선으로 둡니다.

**함께 확인하려던 항목 2개는 원 프로젝트 검증으로 옮겼습니다(§3.13).**

- ~~**Splunk 정합성** — 가격 앵커는 Splunk Cloud(SaaS) 레이트카드인데 모델은 인덱서 서버·저장비를 계산하는 설치형으로 구성되어 있습니다.~~ → 검증 S1·S2
- ~~**오픈소스 유료 지원** — 원장 `self_hosted_license` note가 *"유료 지원 계약을 구매하는 경우는 별도 항목으로 분리 필요"* 라고 명시하나 모델에 없습니다.~~ → 검증 S5

L3에는 Splunk **국내 실거래가**(할인율)와 관리형 역산만 남습니다.

### L4 — 구간 매트릭스 산출
로그량 × 계약기간 × 티어링 × **인건비 시나리오** 4축으로 "이 조건이면 이 선택" 표를 생성합니다.

> **미결 충돌 — 결정 필요.** §3.7이 1회 구매를 연 단위로 나눠 합치는 계산을 금지하므로 **조합 2·4는 5년 총비용도 손익분기도 만들 수 없습니다.** 조합 2·4는 조합 1·3 대비 "디스크만 바꾸면 이렇게 달라진다"는 나란히 비교까지만 가능합니다. (가) 현 결정 유지 — 손익분기는 관리형·조합 1·조합 3 사이에서만 / (나) §3.7 재검토 — 감가 기간 등 가정 수용. 이전판은 대상을 "5개 경로 전체"로 적어 이 충돌을 가리고 있었습니다. §3.3의 구간 폭을 유지해 과잉 정밀도를 금지합니다.

인건비 축은 §3.8에 따라 **전체 / 운영 제외 / 전부 제외** 3종을 병기합니다. 원 모델의 `CostBreakdown` 4분할(software·storage·build·ops)을 그대로 사용하므로 모델 수정은 불필요합니다.

### L5 — 카드뉴스 시리즈 편성

시리즈 구조는 §3.9에 따라 확정되었습니다.

| 편 | 다루는 것 | 역할 |
|---|---|---|
| **1편** | 위탁 vs 직접 — 관리형 기준선 | "당신은 직접 할 구간입니까?" |
| **2편~** | 직접 구축 4개 조합 | 본론 |

에디토리얼 캘린더 + 1편 제작. 편성 원칙은 §6.

**카드 구성 확정 사항** — 사내 드라이브 가격은 SATA·SAS를 나란히 싣고, 필요하면 **연결방식 설명 카드 1장**을 추가합니다(§3.14). SATA는 PC 출신, SAS는 서버 출신이라 값이 다르고, 어느 쪽이 맞는지는 독자의 서버 구성에 달렸다는 내용입니다. 배율은 "항상 1.36배"가 아니라 용량별로 대체로 1.0~1.6배라고 씁니다.

## 6. 콘텐츠 원칙

1. **카드 안에서는 가정을 최소화하고, 링크로 전량 공개합니다.** 카드뉴스는 정보 전달이 최우선이므로 전제를 나열하지 않습니다. 대신 마지막 카드에 전제와 코드 링크를 둡니다 — 그것이 CTA이자 신뢰 장치입니다.
2. **단, 가격 기준 표기는 예외입니다.** "조달청 실계약가 기준" 또는 "정가 기준" 한 줄은 반드시 카드 안에 넣습니다. 이것이 빠지면 할인 조건을 아는 실무자가 첫 장에서 이탈합니다.
3. **매 편은 "당신의 숫자는 얼마입니까"로 끝납니다**(§2).
4. **불리한 결과를 완화하지 않습니다.** 티어링 없는 오픈소스 직접 운영(AWS)이 전 구간 열위라는 사실, 상용 제품에 오브젝트 스토리지를 붙여도 총액의 0.07%로 희석된다는 사실 — 두 가지가 "자기 제품에 불리한 것도 말한다"를 증명하는 핵심 자산입니다.
5. **매 편이 "사세요"로 끝나면 안 됩니다.** 원 프로젝트 간판 결론이 "대부분 구간에서 구매 유리"이므로, 그대로 옮기면 영업 자료로 읽힙니다. 조건과 반증을 앞세웁니다.

### 7.1 진행계획 갱신 규칙 (2026-09-16 신설)

**대상은 링크드인 프로젝트뿐이며, 원 프로젝트는 이 규칙으로도 수정하지 않습니다.**

방향성 변경에 해당하는 것 — 결정 확정·번복, 로드맵 단계 추가·삭제·개명·순서 변경, 분석 구조 재정의, 원칙 신설, 기존 기술이 틀렸음을 발견한 경우.

해당하지 않는 것 — 결정 없이 설명만 오간 질의응답, 단계 내부 작업 진행(`L{n}_result.md` 소관).

**갱신 순서**

1. `CLAUDE.md`를 먼저 고칩니다. 매 세션 자동으로 읽히는 문서이므로 틀린 상태로 남으면 안 됩니다.
2. 본 문서를 **같은 턴에** 동기화합니다.
3. 영향받는 `L{n}_plan.md`를 함께 고칩니다.
4. 틀린 기술은 정정 이력으로 남깁니다.
5. 양쪽 변경 이력에 한 줄씩 추가합니다.
6. 원 프로젝트 무변경을 `git status`로 확인합니다.

**도입 경위.** 질의응답이 이어지는 동안 결정을 모아 뒀다가 나중에 반영하려 했으나, 그 사이 `CLAUDE.md`가 "관리형은 소프트웨어축 선택지"라는 틀린 구조를 담은 채로 남아 있었습니다. 다음 세션이 이를 그대로 읽으면 같은 혼동이 반복되므로, **결정이 나는 즉시 반영**하도록 규칙화했습니다.

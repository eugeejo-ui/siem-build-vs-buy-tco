# L0 — 범위 확정 · 결과

> 2026-09-16 · 상태 **완료** · 다음 단계 **L1 나라장터 API 스파이크**

---

## 1. 이 단계가 답한 질문

착수 시점의 구상은 네 갈래였습니다.

1. 구축 vs 공개 오픈소스 사용 비교
2. 특정 회사 규모에서 재무정보로 로그 사용량 간접 산출
3. 환율·가격정책 변동 시마다 카드뉴스 발행 (상시 변동 → 정기 콘텐츠)
4. 해당 규모에서 어느 방식이 이득이고 어느 시점부터 구축이 이득인지 제시

이 단계는 **네 갈래 중 무엇이 자체 분석 결과로 뒷받침되는가**를 판정했습니다.

## 2. 판정 결과

| 구상 | 판정 | 근거 |
|---|---|---|
| 1 · 구축 vs 오픈소스 비교 | **변경 채택** | 이분법이 아니라 제품 간 비교 매트릭스로 재정의 |
| 2 · 재무정보로 로그량 역산 | **기각** | `phase01 §2.4`가 이미 기각한 방법 |
| 3 · 환율 트리거 정기 발행 | **기각 후 전환** | `phase06 §4.1` 민감도가 지지하지 않음 |
| 4 · 규모별 유불리 제시 | **채택** | 단, 구간(band) 방식으로 |

### 2.1 기각 — 환율 트리거

`docs/phase06_sensitivity.md` §4.1 단변수 민감도:

| 순위 | 항목 | 변동폭 |
|---|---|---|
| 1 | 가격 인상률 | 29.7GB |
| 2 | 탐지룰 공수 | 19.1GB |
| 5 | **환율** | **3.1GB** |

환율 1,360 → 1,480원(+8.8%)에서 손익분기는 44.8 → 41.7GB 이동합니다. 그런데 몬테카를로 80% 구간이 37~56GB로 **폭이 19GB**입니다.

**환율 변동 효과가 모델 자체 불확실성 폭의 약 1/6입니다.** "환율이 올라 구축이 유리해졌다"는 통계적으로 주장할 수 없고, 토네이도 차트가 `README.ko.md`에 공개되어 있어 즉시 반박 가능합니다.

발행 빈도 측면에서도 문제가 있습니다. 환율은 상시 변동하나 **결론은 변하지 않으므로**, 매번 "결론 동일"을 발행하게 되어 시리즈가 조기에 소진됩니다.

**전환:** 환율을 반증 소재로 사용합니다. *"환율 8.8% 올라도 결론은 안 바뀝니다. 바뀌는 것은 갱신 인상률입니다."* 반직관적 훅이면서 자체 데이터가 그대로 뒷받침하고, 진짜 동인(가격 인상률 연 8~12%)으로 독자를 유도합니다.

정기 발행 트리거는 **벤더 가격 개정**으로 대체합니다. Splunk 인제스트 단가는 Splunk 비교에서 48.2GB로 1위 요인입니다.

### 2.2 기각 — 재무정보 기반 로그량 역산

`docs/phase01_organization_profile.md` §2.4가 다단계 추정을 기각한 근거는 오차의 곱셈입니다 — 단계당 2배 오차만으로 5단계 후 32배. 재무정보 기점은 단계가 더 늘어납니다(재무 → 매출 → 트래픽 → PV → API 호출 → 로그량).

원 프로젝트는 이 기각을 근거로 로그량을 입력 변수로 처리했고, `README.ko.md`는 그 판단을 *"결과물이 보고서가 아니라 도구가 된 이유"*로 제시합니다. 파생 프로젝트가 본편 간판 방법론을 뒤집으면 양쪽 모두 무너집니다.

### 2.3 채택 — 구간 방식

**"로그량을 공개하는 기업이 없다"**가 착수 시점의 최대 고민이었습니다. 전제를 뒤집어 해소했습니다.

기업은 **공개를 안 할 뿐 본인은 압니다.** 콘솔에서 1분이면 확인됩니다. 카드뉴스의 역할은 남의 로그량을 추정하는 것이 아니라, 독자가 **자기 숫자를 30초 안에 확인하게 만들고 구간표에 대입**시키는 것입니다.

그리고 정밀도가 필요 없습니다. 80% 구간이 37~56GB라는 것은 모델이 40GB와 50GB를 구분하지 못한다는 뜻입니다.

| 구간 | 서술 |
|---|---|
| ~37GB/day | 답 확정 |
| 37~56GB/day | **단정 불가 — 상담 구간** |
| 56GB/day~ | 답 확정 (티어링 전제) |

리드 관점에서 이 구조가 결정적입니다. 독자가 자기 숫자를 댓글·DM에 적는 순간이 인바운드이고, 그 숫자 하나로 퀄리피케이션이 끝나며, 회색지대는 그대로 상담 요청 구간이 됩니다. **"모른다"를 명시하는 것이 신뢰를 만듭니다.**

### 2.4 채택 — 로그량 외 3개 축 병용

| 축 | 답을 흔드는 폭 | 독자가 아는가 |
|---|---|---|
| 계약기간 3년 vs 5년 | 44GB → **123GB (2.8배)** | **확실히 압니다** |
| 가격 인상률 | 29.7GB (1위) | 갱신 견적서에 있음 |
| 티어링 여부 | 유리 ↔ 전 구간 열위 | 압니다 |

계약기간이 로그량보다 답을 크게 움직이면서 독자가 100% 아는 값입니다. **로그량 추정 문제를 아예 우회하는 축**이므로 시리즈 초반에 배치합니다.

## 3. 데이터 공백 확인

목표(제품 간 가격 비교)와 현행 자산을 대조했습니다.

| 필요 | 현황 | 판정 |
|---|---|---|
| 비교 대상 | 5종 (`src/cost_model.py:38`) | 충족 |
| 인프라 단가 | **AWS 단독** — EBS gp3·io2, sc1·st1, S3 Standard·IA·Glacier, EC2 m6i 서울 리전 | 교체 필요 |
| 온프렘 단가 | **없음.** Dell은 SmartStore 연동 기술 문서만 인용, 계산은 AWS S3 단가로 대체 | **신규 수집** |
| 오픈소스 제품별 | 없음. Elastic·Wazuh를 오버헤드 계수 1개(1.15)로 통합 | 보류 |

`docs/phase08b_presales_dell.md`는 **가격 비교가 아니라 아키텍처 논거**였습니다. 이 점이 이번 확인에서 드러났습니다.

### 조달청 경로의 의미

`docs/phase03_pricing_data.md`에서 부딪힌 벽은 「행정기관 및 공공기관 정보시스템 구축·운영 지침」 제17조에 따른 **시스템 구성 비공개**였습니다. 이 조항은 *운영 시스템 구성*에 적용되며, **물품 계약 단가는 공개 대상**입니다. 온프렘 스토리지는 물품입니다.

**벽이 있는 영역과 없는 영역이 달랐습니다.**

더 중요한 것은 이것이 정가가 아니라 **실계약가**라는 점입니다. `docs/phase04_tco_engine.md`가 스스로 적은 최대 약점 — *"해외 정가 앵커(실계약은 25~70% 할인)"* — 을 정면으로 해소합니다. 카드 문구가 "정가 기준"에서 **"조달청 실계약가 기준"**으로 바뀌며, 방어 문구가 셀링 포인트가 됩니다.

**단, 미검증입니다.** 품목 분류·용량 필드·벤더 식별 가능 여부를 확인하지 않았습니다. L1이 이것만 판정합니다.

## 5. 확정한 범위

**포함:** 온프렘 벤더 확장(선행) · AWS 공식 API 전환 · 구간 매트릭스 · 카드 시리즈 · 가격 개정 트리거

**제외:** 오픈소스 제품 분화(L6 이후 재검토) · 환율 트리거 · 로그량 추정

**배치:** 별도 저장소로 분리하지 않고 `linkedin/` 하위에 격리. 가격 수집과 온프렘 모델이 `data/pricing.yaml`·`src/cost_model.py`를 직접 수정하므로, 분리하면 가격 원장이 두 벌이 되어 단일 원장 원칙이 깨집니다.

## 7. 다음 단계에 미치는 영향

L1은 **단일 질문에만 답합니다** — 나라장터 API에 온프렘 스토리지 단가가 쓸 만한 형태로 존재하는가.

트랙 B 전체가 이 하나에 걸려 있습니다. 모델(L3)부터 착수하면 데이터가 없을 때 전부 폐기하게 되므로, **판정을 먼저** 내립니다.

**중단 조건:** 품목 분류·용량 필드·벤더 식별 중 둘 이상이 불가하면 트랙 B를 폐기하고 해외 리스트가(트랙 C)로 후퇴합니다.

**선행 조건:** 공공데이터포털 활용신청 후 인증키 확보 (사용자 조치 필요).

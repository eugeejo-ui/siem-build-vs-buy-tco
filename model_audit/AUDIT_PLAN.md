## 0. 이 프로젝트의 위치

| | 원 분석 프로젝트 | **원 프로젝트 검증 (본 프로젝트)** | 링크드인 카드뉴스 |
|---|---|---|---|
| 위치 | `docs/`·`src/`·`data/`·`tests/`·`outputs/`·`README*.md` | **`model_audit/`** | `linkedin/` |
| 관계 | 검증 대상 | 원 프로젝트를 검증하고, **승인받은 오류만** 원 프로젝트에 반영 | 원 모델 산출값을 사용. **L2는 본 검증 이후 재개** |

**링크드인 프로젝트와 별개입니다.** 링크드인 단계(L0~L6)에 속하지 않으며 링크드인 코드를 불러 쓰지 않습니다. 순서만 링크드인 L2보다 앞섭니다.

> **경위:** 처음에는 링크드인 단계 **L2-0**으로 신설했으나, 검증 대상이 원 프로젝트이므로 같은 날 폐기하고 별개 프로젝트로 분리했습니다.

## 1. 목적

**원 프로젝트가 계산한 두 경로의 5년 비용을 그대로 믿지 않고, 비용 항목마다 근거부터 다시 구합니다.**

| 검증 대상 | 원 프로젝트 선택지 |
|---|---|
| **AWS 임대 + 오픈소스** | `self_hosted`, `self_hosted_tiered` |
| **AWS 임대 + Splunk** | `splunk` (재현·공통 수정만: `splunk_smartstore`) |

관리형 SIEM(`managed_siem`)은 손익분기의 비교 상대로만 씁니다. 관리형 가격 자체의 검증은 링크드인 L3 소관입니다.

**왜 중요한가** — 원 프로젝트 결론("하루 약 37GB 미만이면 구매 유리")과 링크드인 카드의 수치(L2의 AWS 쪽 금액, 손익분기, 비용 구성)가 모두 이 두 경로의 값에서 나옵니다. 틀리면 둘 다 왜곡됩니다.

## 2. 진행 절차 — 승인 관문이 하나 있습니다

```
V1 재현 확인 ─▶ V2 영향 측정 ─▶ V3 근거 확인 ─▶ V4 판정·기록 ─▶ V5 보고
                                                                   │
                                                          ◆ 사용자 승인 ◆
                                                                   │
                                              V6 원 프로젝트 수정 ─▶ V7 수정 후 검증
```

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| **V1 재현 확인** | 독립 계산기를 만들고, 원래 가정으로 원 모델과 **원 단위까지 일치**하는지 확인 | `audit_calc.py`, `verify_audit.py` |
| **V2 영향 측정** | 점검 항목마다 가정 **하나만** 바꿔 5년 총비용·손익분기 변화 측정 | `out/impact.json` |
| **V3 근거 확인** | 영향 1% 이상 항목을 1차 출처로 확인 | 항목별 출처·확인일 |
| **V4 판정·기록** | 항목 판정. **오류·가정 선택은 원 프로젝트 phase별 파일에 기록** | `findings/phaseXX_*.md` |
| **V5 보고** | 판정 집계, 원 모델값 대 검증값, 수정안 목록 | `AUDIT_REPORT.md` |
| ◆ **승인** | 사용자가 **항목별로** 수정 여부 결정 | 보고서 승인란 |
| **V6 수정** | **승인된 항목만** 원 프로젝트에 반영 | 원 프로젝트 커밋 |
| **V7 수정 후 검증** | `pytest`, `src/verify_consistency.py`, 문서 수치 동기화, 차트 재생성 여부 확인 | `AUDIT_RESULT.md` |

**승인 전에는 원 프로젝트를 한 글자도 고치지 않습니다.** V1~V5는 `model_audit/` 안에서만 작업합니다.

## 3. 계획 수립 중 코드에서 이미 보인 의심 지점

`src/cost_model.py`·`src/storage_model.py`·`src/tco_engine.py`·`data/pricing.yaml`을 읽으며 확인한 **사실**입니다. **영향 크기는 아직 재지 않았습니다.**

"사실이면"은 그 지점이 확인될 때 어느 쪽 비용이 **실제보다 어떻게 계산되어 있는지**를 뜻합니다.

| 지점 | 원 모델의 현재 상태 | 사실이면 | 근거 위치 |
|---|---|---|---|
| Splunk 가격의 성격 | 가격 기준은 **Splunk Cloud**(인프라 포함 구독) 요금인데, 서버·디스크를 AWS 요금으로 **따로 또** 계산 | 구조 판정 필요 | 원장 `splunk_ingest` source |
| Splunk 90일 초과 보관 가산 | 원장에 30~50%(base 40%)가 있으나 **`src/` 어디에서도 쓰지 않음**. phase02는 비용 항목으로 적어 둠 | Cloud라면 Splunk 과소 | `grep` 0건 · `phase02` 60행 |
| Splunk 인건비 | 구축 0원, 운영은 ISMS 대응분(연 1.5인월)만 | 설치형이라면 Splunk 과소 | `cost_model.py:264`, `:289` |
| Splunk 복제 | 사본 없음(`rf=1, sf=1`)인데 서버는 최소 3대(HA). 원 문서도 "기본값 미확정, 사본 1벌로 둠" | Splunk 과소 | `cost_model.py:62-63` · `phase10` 171행 |
| Splunk 서버 구성 | 인덱서만 셈. ES 검색 헤드·클러스터 관리 서버 등 없음 | Splunk 과소 | `cost_model.py:237-239` |
| Splunk 인덱서 사양 | 서버 단가가 8코어·32GB급(`m6i.2xlarge`) 하나. ES 권장 사양과 맞는지 미확인 | Splunk 과소 가능 | 원장 `compute_price` |
| 오픈소스 0원과 기능의 양립 | 70%를 S3에 두고도 **검색 가능**하다고 가정. 무료판에서 되는지 미확인 | 안 되면 오픈소스 과소 | `compute_storage_elastic()` |
| 오픈소스 서버 1대당 용량 | 15TB/대의 근거는 "힙 31GB 노드"(메모리 60GB 이상급)인데, 서버 단가는 메모리 32GB급 | 오픈소스 과소 | 원장 `sizing_tb_per_node_selfhosted` |
| 오픈소스 서버 대수 | **S3에 둔 용량까지** 합쳐서 대수를 셈 | 오픈소스 과대 | `cost_model.py:241-243` |
| S3에도 사본 ×2 | 총량에 `(1 + 복제본)`을 곱한 뒤 70%를 S3로 보냄 | 오픈소스 과대 | `storage_model.py` elastic 본문 |
| 오픈소스 로컬 저장 | 로컬 30%를 전부 SSD 단가로. Splunk는 일부를 HDD로 | 오픈소스 과대 | `cost_model.py:197-201` |
| 1년차 보관량 | 매년 "그해 로그량 × 730일". 1년차부터 2년치가 차 있다고 가정 | 양쪽 과대 (오픈소스가 더 큼) | `tco_engine.py:80-86` |
| 서버 요금 | 온디맨드 정가. 5년 운영에 약정 할인 미반영 | 양쪽 과대 | 원장 `compute_price` note |
| AWS 부가 요금 | 가용영역 간 전송료, 스냅샷, S3 요청료 등이 **0원** | 오픈소스 과소 | 모델에 항목 없음 |
| S3 구간 체감 | `object_price` 0.025 단일값. 실제는 50TB↑ 0.024, 500TB↑ 0.023 | 대용량에서 오픈소스 과대 | 원장 `object_price` |

**방향이 섞여 있습니다.** 하나씩 재서 **합친 결과가 어느 쪽으로 가는지** 확인해야 합니다. 원 프로젝트 결론이 움직일 수도, 그대로일 수도 있습니다. **모두 가설이며**, 원 모델이 의도적으로 고른 가정일 수 있습니다.

## 5. 방법

### 5.1 독립 계산기와 재현 확인 (V1)

위 항목 중 상당수(C1·D1·D2·D4·C4 등)는 **원장 값만 바꿔서는 고칠 수 없고 계산식 자체를 바꿔야 합니다.** 원 모델 코드는 승인 전에 고칠 수 없으므로, 두 경로의 계산을 한 줄씩 드러낸 **독립 계산기**를 `model_audit/` 안에 만듭니다.

1. **재현 확인** — 원래 가정으로 돌렸을 때 원 모델 `compute_tco()` 결과와 **원 단위까지 일치**해야 합니다. 일치하지 않으면 다음 단계로 가지 않습니다.
   - 대상: `self_hosted`·`self_hosted_tiered`·`splunk`·`splunk_smartstore`
   - 조건: 10·20·50·100GB/day × 3·5년 × low/base/high × 로그 증가 반영/고정
   - 원장 값은 `pricing_loader.load()`로 **읽기만** 합니다.
2. **한 번에 하나씩 바꾸기** (V2) — 점검 항목마다 **그 가정 하나만** 바꿨을 때 5년 총비용과 손익분기가 얼마나 움직이는지 잽니다.

재현 확인은 계산기를 고칠 때마다 다시 돌립니다.

### 5.2 깊이 (V3)

- 5년 총비용(50GB/day, base) 영향 **1% 미만**이고 손익분기 영향 **1GB/day 미만**인 항목은 판정만 하고 외부 조사를 생략합니다.
- 그 외 항목은 1차 출처를 확인합니다.

### 5.3 출처

| 대상 | 출처 |
|---|---|
| AWS 단가·약정 요금·전송료 | **AWS Price List Bulk API** (인증 불필요) |
| Splunk 요금 체계·사양·복제 | Splunk 공식 문서·가격 페이지 |
| Elastic·OpenSearch·Wazuh·Graylog 무료판 기능, 사이징 | 각 공식 문서·구독 비교표 |
| 인건비 | 한국소프트웨어산업협회 공표 |

- 검색 요약은 그대로 쓰지 않고 원문이나 복수 출처로 교차 확인합니다(링크드인 L2에서 검색 요약이 드라이브 연결방식을 틀리게 알려준 사례).
- 출처마다 URL과 확인일을 남깁니다.
- AWS 가격 수집 코드는 본 프로젝트 안에 따로 둡니다. 링크드인 코드를 불러 쓰지 않습니다.

### 5.4 종합 (V5)

- **검증값 A** — "오류" 항목만 고친 값
- **검증값 B** — "가정 선택" 항목까지 반영한 범위
- 원 모델값 대 검증값을 항목별로 나란히 놓고, 차이가 어느 항목에서 왔는지 분해합니다.

### 5.5 중단·재분류 조건

- **S1을 공개 자료로 확정하지 못하면** — Cloud 구조와 설치형 구조를 둘 다 계산해 "가정 선택"으로 둡니다.
- **Splunk Cloud 구조가 맞다고 판정되면** — "AWS 임대 + Splunk"라는 선택지 정의 자체가 달라지므로 보고서에서 **결정을 요청**합니다(원 프로젝트 선택지 재정의, 링크드인 결정 트리 경로 추가 여부).
- **항목이 늘어 예상 소요를 크게 넘기면** 즉시 보고하고 재분류합니다.

## 6. phase별 기록 파일 (V4)

**오류·가정 선택·근거 부족이 나온 원 프로젝트 phase마다 파일 하나**를 만듭니다. 파일명은 원 프로젝트 문서명을 따릅니다.

```

  phase03_pricing_data.md
  phase03b_storage_layer.md
  phase04_tco_engine.md
```

한 항목이 두 phase에 걸치면 **원인이 있는 phase**에 기록하고, 다른 phase 파일에는 참조만 남깁니다.

| 원 프로젝트 위치 | 파일:행 |

## 8. 링크드인 프로젝트와의 관계

- 링크드인 L2(디스크 단가 비교표)는 **본 검증이 끝난 뒤 재개**합니다. L2의 AWS 쪽 금액과 배율이 원 모델 산출값에 기대기 때문입니다.
- 본 검증이 끝나기 전까지 링크드인 문서의 원 모델 수치(비용 구성표, 인건비 시나리오 표, L5 훅)는 **카드에 쓰지 않습니다.**
- 원 프로젝트가 수정되면 링크드인 문서의 해당 수치를 갱신합니다(링크드인 진행계획 갱신 규칙에 따름).
- 링크드인 문서에 적혀 있던 원 프로젝트 수정 후보(S3 구간 체감)와 확인 항목(Splunk Cloud 앵커 정합성, 오픈소스 유료 지원)은 본 프로젝트로 옮겼습니다(D9·S1·S5).

## 9. 하지 않는 것

- **승인 전 원 프로젝트 수정 일체**
- 관리형 SIEM 가격 검증 — 링크드인 L3 소관
- Splunk **국내 실거래가**(할인율) — 링크드인 L3 소관. 본 검증은 가격의 **구조**(무엇이 포함된 요금인가)만 봅니다
- 사내 장비 경로 — 링크드인 L2 소관
- 몬테카를로 재실행 — 필요하면 V5 보고 때 제안
